# 玩法多样性第四批：城市特色菜系 · 研发树 · 成就奖励食谱（V10）

> 四项需求的实现说明：数据结构变更、研发树接入、城市切换刷新、成就注册判定。

---

## 一、需求 → 实现对照

| 需求 | 实现 |
|---|---|
| ① 城市特色菜系（食材 + 菜品） | 14 座城市各 1 个特色菜系 + 2~3 种专属原料 + 3 道菜（42 款） |
| ② 食谱城市绑定 + 切换刷新 + UI 标示 | `recipe.city` 字段 + `refreshCityMenu()` + 城市条 |
| ③ 研发树（分组/阶段/前置/依赖） | `RESEARCH_TREE`（55 节点 / 5 阶段）+ `treePrereqOk()` |
| ④ 成就奖励稀有食谱（不在树上、幂等） | `ACH_RECIPES`（7 款）+ `grantAchRecipe()` |

## 二、数据结构变更

### 1. `ING`（原料表）新增 `origin` 字段

```js
{ id: 'sichuanpep', name: '汉源花椒', base: 5.6, origin: '510100' }
//                                                       ^^^^^^^^ 产地城市 id
```

**为什么加在主表而不是另开一张"城市原料"表**：
原料参与采购价、库存、扣料、备货、进货建议、成本核算等六七条链路。
另开一张表的话，每条链路都要写"先查主表再查城市表"的分支，漏一处就是
"能做但买不到"或"扣料时读错价"这类**静默** bug。放在同一张表，
`origin` 只是多一个筛选维度，主流程一行都不用改。

`ingAvailableAt(ingId, cityId)` 是唯一的判定入口：`origin` 为空 = 全国有货。

### 2. `CUISINES`（菜系表）新增 `city` 字段

`city` 为空 = 全国通用（5 个）；非空 = 该菜系**只在对应城市存在**（14 个）。

**为什么不把城市菜并入通用系**：城市特色菜的卖点是**地域身份**，不是口味标签。
若并入（例如成都的藤椒菜算"鲜果茶系"），玩家在任何城市都能做，
"来成都开店"这件事就没有意义了。

### 3. `RECIPES`（配方表）新增两个字段

```js
{ id: 'cd_mala', cuisine: 'cd_rattan', city: '510100', tier: 3, ... }
//                                          ^^^^^^^^ 绑定城市
{ id: 'ach_golden', ach: true, ... }
//                        ^^^^^^^ 成就专属标记
```

`tier` 直接复用为**研发阶段**（1~3），避免两处数字各说各话。

### 4. 新增三张表

| 表 | 内容 |
|---|---|
| `RESEARCH_TREE` | 55 个节点：`{ id, recipe, stage, prereq[], city }` |
| `ACH_RECIPES` | 7 款成就专属食谱，**不在树上**、无 `research` 字段 |
| `WORKSHOP_*` 扩展 | 城市系工坊（14 条），造价 ¥420 起、降本 18%、研发折扣仅 20% |

## 三、研发树节点的接入方式

### 节点结构

```js
{ id: 'n_cd_mala', recipe: 'cd_mala', stage: 3,
  prereq: ['n_cd_douban'], city: '510100' }
```

### 前置判定（`engine.treePrereqOk`）

```
前置节点 → 查 treeNodeById → 取其 recipe → 是否在 s.recipes 里
```

- **前置指向不存在的节点 → 视为不满足**（数据写错要能被发现，不能静默放行）
- **成就奖励的配方也算满足**（玩家拿到就是拿到，不该被树卡住）

### `canResearch` 的判定顺序（顺序很重要）

```
① 不是可研发配方 / 已解锁        → 无法研发
② r.city ≠ 当前城市             → 「只能在成都市研发」   ← V10 新增
③ 研发树前置未满足              → 「需先研发「豆瓣奶绿」」 ← V10 新增
④ 现金不足                      → 现金不足
⑤ 城市专属原料在本地买不到→ 「需在成都市才能买到藤椒油」 ← V10 新增
⑥ 原料不足                      → xxx 不足
```

### 为什么城市前置不违背 V9 的教训

V9 出事的是「**花钱门槛**」—— 玩家算不出划不划算，于是配方被永久锁死
（6 款 tier3 解锁率 19/20 → 0/20）。

这里是「**地域边界**」—— 研发页**按城市分组显示**，玩家一眼看懂
"这些菜只能在这座城做"，不存在"不知道被锁了"的情况。

> 同一个词"前置"，性质完全取决于玩家能不能看懂。
> 看不见的锁是陷阱，看得见的锁是玩法。

## 四、城市切换的数据刷新逻辑

`setVenueCity()` 内部调用 `refreshCityMenu()`，刷新**四样**东西
（少一样就会出"看起来能点但点了没反应"）：

| # | 刷新对象 | 处理 | 不做会怎样 |
|---|---|---|---|
| ① | **菜单** | 移出本店城市用不上的配方 | 备货去买买不到的原料 → "菜单里有的菜做不出来" |
| ② | **菜单兜底** | 空了就补一款本城能做的 | 当天开不了门 |
| ③ | **库存** | 清除异地专属原料（退还资金） | 现金全压在用不掉的原料上 |
| ④ | **工坊等级** | **保留**（换回来还能用） | 白花的钱 |

**已解锁的异地配方保留在 `s.recipes` 里**，只是不能上架 ——
研发投入是跨城市资产，换城只是换了一个可上架的池子。
若解锁即绑定、换城即失效，玩家第 5 天换城市会发现前面全白研了，
那是惩罚而不是取舍。

返回结构供 UI 直接用：

```js
{ ok, cityName, dropped: [...], kept: [...],
  cityCuisines: ['gz_canton'], cityIngs: ['tea_gj', 'pomelo'] }
```

UI 的 toast 会播报实际影响：「已切换到成都市 · 2 款本地菜下架 · 当地特色：巴蜀麻辣系」。

### 存量存档的同一条路径

`sanitizeState` 末尾也调`refreshCityMenu()` ——
场景：玩家在成都导出存档，在北京的存档里读档，菜单里还留着成都菜。
不刷新就会去备货买不到的材料。

## 五、成就系统的注册与判定流程

### 注册（`data.js`）

```js
{ id: 'a_ach_golden', name: '鎏金传说', desc: '口碑达到 99',
  reward: { cash: 2000, bp: 10, recipe: 'ach_golden' },   // ← recipe 是新增字段
  check: s => (s.rep >= 99) }
```

新增 12 条：4 条城市风味 + 1 条研发树大师 + 7 条成就食谱奖励。

**成就总量变化 → 连带重标 BP_START_RATE**：
★ 从 150 涨到 239，若不改 `rate`，满星玩家会拿到 ¥695 启动资金
（比 150★ 时代的 ¥550 高 26%），等于给老玩家一次无声的数值增强。
`rate` 由 45 降到 30，满星仍是 ¥463（封顶不变）。

### 判定（`checkAchievements`）

```
遍历 ACHIEVEMENTS：
  if (s.ach[a.id]) continue;          // 已达成过 → 跳过（幂等的第一道）
  if (!a.check(s)) continue;
  s.ach[a.id] = true;
  s.cash += a.reward.cash;
  if (a.reward.recipe) grantAchRecipe(s, a.reward.recipe);   // ← 新增
```

### 发放与重复处理（`grantAchRecipe`）

| 情况 | 处理 |
|---|---|
| 未解锁 | 推入 `s.recipes` + 日志「📜 成就奖励食谱」 |
| **已解锁** | **不重复推入**，但**现金照常发** + 日志「你已拥有，奖励现金照常发放」 |
| 城市不匹配 | 额外提示「需前往成都市才能上架」 |
| 食谱 id 不存在 | 返回 `{ok:false}`，**不抛错** |

**为什么不因为"配方重复"而吞掉现金**：那是玩家应得的另一份奖励。
达成成就和获得配方是两件事，不该因为其中一件重复就撤销另一件。

**幂等保证**：`s.ach[a.id]` 一旦为 true 就不再判定，
加上 `grantAchRecipe` 自身的 `includes` 检查，双重保险。

## 六、UI 呈现

### 城市条（菜单页 + 研发页顶部）

```
📍 成都市·四川省
   本店可用菜系 7 个 · 本地特色：🌶️巴蜀麻辣系
   🌶️藤椒油  🫘郫县豆瓣  🍂川陈皮
   💡 在「🏙️ 经营信息」里切换城市可研发当地特色菜；已解锁的异地配方会保留
```

### 研发页（按城市分组 + 阶段 + 前置）

```
🌐 通用配方 · 全国都能做
  第 2 阶段 · 需先做「芝士奶盖绿茶」
  ┌────────┬────────┐
  │芋泥波波 │ 生椰拿铁 │
  └────────┴────────┘

🗺️ 广州市              不在本店
  （弱化 + 禁用，点击提示「需切换到广州市才能研发」）

📍 成都市 · 本店
  第 1 阶段 / 第 2 阶段 / 第 3 阶段...
```

### 菜单页的异地配方

不隐藏（隐藏会让玩家以为配方丢了），标 🗺️ 徽章 + 置灰 + 说明原因。

### 原料市场

只列**当前城市买得到**的原料，本地特产高亮显示。
（全列的话，北京玩家会看到 20+ 行「藤椒油 ¥3.5」点下去没反应。）

## 七、这一轮抓到的缺陷（都是断言抓出来的，不是 review 发现的）

| # | 缺陷 | 症状 | 根因 |
|---|---|---|---|
| 1 | **城市菜用外城原料** | 「成都的藤椒青提」提示"需在绵阳才能买到汉源花椒" | 写数据时没检查 `origin` 与 `city` 一致 |
| 2 | **`sakura`/`star` 未接入研发树** | 能跳过前置直接研，树的规划性对它们失效 | V9 批次追加配方时漏挂节点 |
| 3 | **`autoFill` 遍历全部原料** | 一键补货毫无反应 | 29 种原料里 20+ 种本地买不到，挤占采购额度 |
| 4 | **市场列出买不到的原料** | 按钮点了没反应，像坏了 | 同上 |
| 5 | **「32 条共 150★」硬编码三处** | 数字全错，但页面照常渲染 | 数字由数据推导却写死在文案里 |
| 6 | **脚本改数据串位** | `price: 35, tier: 3` → `ptier: 3`，售价变undefined | 批量替换正则太宽松 |
| 7 | **`citiesVisited` 漏记新城市** | 「经营过3 城市」少算一个 | 只记了切换前的城市 |
| 8 | **★ 总量涨了没重标资金曲线** | 满星玩家开局资金 +26% | 成就★ 与 `BP_START_RATE` 的隐式耦合 |

**#1 / #6 特别值得记**：两者都是"数据写错了但没有任何报错"——
页面照常渲染，只是数值在骗人。这类缺陷只能靠**断言主动查**，
不能指望运行时报警（M0c 跨城原料检查 / M0f 必填字段检查）。

## 八、回归锁

### probe新增 M 组 56 项（279 项全绿）

| 组 | 守住什么 |
|---|---|
| M0 | 数据自洽：菜系/原料的城市 id 有效、**城市菜只用本城原料**、定价高于通用均值、**必填字段非undefined** |
| M1 | 研发树：节点 id 唯一、可研配方全部接入、**前置指向更早阶段（无环无倒置）**、节点与配方 city 一致 |
| M2 | 城市绑定：属地可研、异地不可研、异地已解锁**保留但不可上架**、专属原料只在本城 |
| M3 | 切换刷新：菜单移除异地菜、菜单不空、配方保留、原料清空、**往返切换幂等** |
| M4 | 成就食谱：**不在研发树**、无 research、canResearch 不放行、正反向引用完整、**重复发放幂等** |
| M5 | 展示模型：城市分组、本城无 away 节点、状态合法、成就组单列 |
| M6 | 存量兼容：老存档补字段、脏数据清洗、菜单收敛、**幂等**、版本号不变 |

### 全量回归

```
probe 279 · dom-smoke · browser-smoke 144 · minigame-smoke 221
mobile-smoke 31 · symbol-check · xss-verify                ← 7 套全绿
sim 24 局：easy 203% / normal 102% / hard 84%
```

相对 V9（206% / 96% / 76%）：easy −3pp、normal +6pp、hard +8pp。
BP_START_RATE 降低后 AI 的开局现金更紧，反而更早进研发树形成正循环 —— 幅度健康。
