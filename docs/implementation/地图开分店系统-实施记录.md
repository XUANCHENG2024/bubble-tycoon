> 需求五项：店铺体系 / 店长与托管 / 店长 AI / UI 交互 / 存档兼容。
> 设计文档见《../design/地图开分店系统-设计.md》，本文记录**实际实现**与踩坑。

---

## 一、核心决策：`s.stores[]` 权威，`s.shops` 降级为派生值

### 为什么这么设计

现有 `s.shops` 是**数字**（1 = 只有总店，2~4 = 有分店），它同时表达三件事：
有几家店、店号范围、店的位置。新需求要"任意位置开店 + 每店独立位置/名称/等级/账本"，
数字**表达不了** —— 必须变对象数组。

但 `s.shops` 在 engine.js 里有 **19 处**使用点（客流、租金、AI、清洗…）。
直接改成数组 = 19 处全改，且极容易漏（漏一处就是"开了店但店号算错"的静默 bug）。

**解法**：`s.stores` 是权威，`s.shops = s.stores.length` 是派生值。
既有 19 处代码**一行都不用改**，改动只发生在增删店的少数几处，
且那几处统一走 `syncShopCount(s)`。

**同步点只有这一个** —— 任何增删店都必须调它。
散落着写 `s.shops = X` 就会漂，而"店数漂了"的表现是客流/租金/名额全错且不报错。

## 二、字段设计

```js
{
  id: 1,                  /* 稳定 id（不随顺序变化） */
  branch: 1,              /* 店号：1 = 总店，2+ = 分店。
                             与 staff.branch / manager.branch 对齐，
                             既有 staffOfBranch(s, b) 不用改 */
  name: '总店',            /* 玩家可改 */
  emoji: '🏠',
  cityId: '110100',       /* 所在城市（决定可用菜系） */
  venueType: 'community', /* 场地类型（决定客流特征） */
  lng: 116.407, lat: 39.909, coordSys: 'GCJ02',
  isMain: true,           /* 主店标记，全表唯一 */
  level: 1,               /* 店铺等级 1~10 */
  auto: false,            /* ★ 托管标记：true = 交给店长 */
  managerId: null,        /* 该店店长（null = 玩家亲自经营） */
  cash: 0,                /* 该店自有资金 */
  inv: {},                /* 该店独立库存 */
  income: 0, expense: 0, cups: 0, days: 0,
  lastReport: null, history: [],   /* 经营报表 */
  upgrades: {},
}
```

`id` 与 `branch` 分开：`id` 稳定（存档引用用），`branch` 是显示序号。
将来若实现关店导致序号重排，存档里的引用不会错乱。
**数据结构改一次很贵，先改对。**

## 三、店长名额规则变更（V11 → V12）

| | 规则 |
|---|---|
| V11 | `店数 − 1 − 已招数`（总店不设店长） |
| **V12** | `店数 − 已招数`（**含主店**） |

需求明确「每家分店最多任命 1 名店长（**含主店**）」。

### 连带改动清单（漏一处就是"测试全绿但规则已错"）

| 位置 | 改动 |
|---|---|
| `managerSlotsLeft` | 去掉 `− 1` |
| `managerOfBranch` | `branch >= 2` → `>= 1` |
| `refreshManagerCandidates` | `branch >= 2` → `>= 1` |
| `dailyManagerRefresh` | 循环从 `b = 2` → `b = 1` |
| `hireManager` | 允许总店；与 `assignManager` **合并**（见下） |
| 清洗：店长 branch 范围 | `2..shopN` → `1..shopN` |
| 清洗：名额硬顶 | `shopN - 1` → `shopN` |
| 清洗：候选池店号 | `>= 2` → `>= 1` |
| probe N1/N5/N6 组 | 断言语义更新 |
| browser-smoke / e2e-flow | 断言语义更新 |

### 合并 `hireManager` 与 `assignManager`

V11 有 `hireManager`（招到分店），V12 又加了 `assignManager`（任命到店），
两个函数做同一件事、**规则还不一致**（一个不允许总店、一个允许）。
合并为一个入口后规则只有一处，不会出现"两个入口规则不同"这种经典 bug。

## 四、店长 AI 每日经营

### 为什么托管店要独立结算

实时模拟需要玩家逐个点出杯位 —— 托管的店玩家不在场，
塞进去的结果是「玩家不操作它就一天做不了单」。所以走**日结算模型**。

### 单店结算流程

```
1. 无员工 → 空店：零产出，但扣固定开支（玩家要看到"这家店白开着"）
2. 客流 = (4 + 口碑×0.36) × 等级加成 × 场地系数 × 难度系数
3. 店长加成（managerBonus，与玩家经营同一套）
4. 出杯 = 客流 × 0.72 × 员工平均效率 × 速度加成
5. 营收 = 出杯 × 均价 × 0.92（折价与未满座损耗）
6. 成本 = 原料(34%) + 工资 + 固定开支(按等级)
7. 采购：店长自己补料，只买本城能买到的
8. 净利入店账；累计营收达阈值 → 店铺升级
9. 生成报表 → lastReport + history(近 7 天)
```

### 场地类型系数

| 类型 | 系数 | 类型 | 系数 |
|---|---|---|---|
| 交通枢纽 | 1.30 | 社区 | 1.00 |
| 景区 | 1.25 | 医院 | 0.95 |
| 步行街 | 1.18 | 厂区 | 0.90 |
| 校园 | 1.15 | 乡镇 | 0.80 |
| 商场 | 1.12 | 写字楼 | 1.05 |

### 关键：托管店不计入 `activeBranchCount`

托管店的营收来自日结算，不来自实时模拟。
若它还计入客流加成，**玩家经营的总店会凭空多出客流** ——
相当于"白送一个分店的客流却不用管它"，托管会变成稳赚的偷懒选项。

这是本轮最容易被漏掉的一处联动，已写成断言 S5b。

## 五、启动资金

开店时从总部划拨 `MANAGER_START_CASH = 2000`。

**没有它，店长 AI 开局就一分钱都没有** —— 买不了料、付不出工资，
托管的店永远是空转，玩家会看到"托管 = 亏钱"，那就不是有意义的委托。

这笔钱同时是**玩家对这家店的风险敞口**：亏了是真亏（不返还），赚了店长分成。
玩家可以随时**注资**（总部 → 店）或**提现**（店 → 总部）。

## 六、UI

### H5 端：`storesPanelHtml(s)`，挂在「🏙️ 商圈」页最前面

店铺与商圈是同一语义（在哪、开什么店），放这一页比塞进管理页或升级页都自然。
放最前面是因为它是这一页的**主功能**，竞争对手只是背景信息。

每店一张卡：店名 / 主店标记 / 等级 / 城市 / 场地 / 编制 / 四项经营数据 /
店长信息 / 最近报表 / 操作按钮（接管⇄托管、任命、撤下、设为主店、注资、提现、改名）。

### 开店流程

「＋ 开设新店」→ 弹窗（省份下拉 + 城市下拉 + 场地类型网格 + 店名）→ 确认。

**位置从哪来**：城市表自带 GCJ-02 经纬度（`CITY_CENTERS`），选城市即自动定位。

### ⚠️ 为什么不内嵌地图 SDK

沿用现有「经营信息」面板的既定论证（js/ui.js 里写得很清楚）：
静态托管的离线包拉不到高德瓦片 → 地图区空白 → **反而像坏了**。
用户可在高德地图选好点复制坐标回来填，或直接手输经纬度。
340+ 城市可选，等于"任意位置"。

### Canvas 端：`panelStores(ctx, x, y, w, s)`，同位置同语义

Canvas 没有 `<select>`，用**循环切换**（点一次切下一个城市/场地）——
这是本项目既有的做法（经营信息里的省市切换就是这样），不引入新交互范式。

**两版必须对等** —— Canvas 是独立后端，只测 H5 的话
"小游戏端没有这个系统"这类问题不会被发现。

## 七、存档兼容

### 老存档迁移

老存档只有 `s.shops`（数字），没有 `stores`。清洗时把数字还原成店铺数组：

```
stores 为空 → 生成 shopN 家店（branch 1 = 总店且为主店，其余按序）
stores 缺总店 → 补一个（总店不可缺失）
stores 缺店号 → 按 s.shops 补齐（见下）
主店多个 → 只留第一个；一个都没有 → branch 最小的设为主店
```

### ⚠️ 一个真实缺陷：stores 数量少于 s.shops 时必须补齐

场景：脏存档里 `s.shops=3` 但 `stores` 只有 1 家（总店）。
若不补，店号 2/3 的店长会在后续清洗里被当成"店号越界"丢弃 ——
**表现是「玩家的店长凭空消失」**。

补齐逻辑按 `s.shops` 逐个检查缺失的店号。

### 店长清洗（V12 规则）

| 情况 | 处理 |
|---|---|
| branch < 1 或 > 店数 | 丢弃 |
| 同一家店两个店长 | 保留一个，其余丢弃 |
| 店长数 > 店数 | 裁剪（白嫖是最难查的平衡漏洞） |
| `nextMgrId` ≤ 现存最大 id | 修正为 max+1 |
| 候选池店号越界 | 清除 |

### 店长的双向引用

`store.managerId` 与 `manager.branch` 存了同一关系，
**必须**有单一同步点 `syncStoreManagers(s)`。
不一致的后果很具体：加成一店算两次、工资付两次，或店长管着别人的店。

清洗时：店长表里没有的 → 清掉店上的 `managerId`（孤儿引用）；
`auto=true` 但没店长的 → **取消托管标记**（否则留下"托管中但没店长"的死店）。

## 八、这一轮踩的坑

### 1. `newGame` 忘了建总店 → 店号错位

`s.stores` 初始为空 → `syncShopCount` 把 `s.shops` 算成 0 →
之后 `openStore` 开出的第一家店拿到 **branch 2**（跳过 1）。

**表现是「有 1 家店但它叫第 2 家」** —— 静默发生，不报错。
修法：`newGame` 里显式建总店。

### 2. `cityGeoOf` 对无坐标城市返回 null

`makeStore` 与清洗处都直接取 `.lng` → TypeError。
兜底用 `GEO.FALLBACK`。

### 3. 规则变更后断言没同步 → 假象

N1a~N1e、N5g、N6c~N6e 断言的都是 V11 旧语义。
**测试全绿但规则已错** —— 这是规则变更最典型的配套遗漏。

### 4. 断言写错：注资/提现的"守恒"

我原本断言"注资 1000 再提现 500 后现金回到原值" ——
那是把"注资额 = 提现额"当成了前提，而实际操作不等额。
正确写法是断言**净变化**（总部 −500、店铺 +500）。

### 5. `s.shops` 与 `stores` 冲突时谁说了算

`stores` 是权威 → 清洗末尾 `syncShopCount(s)` 无条件覆盖 `s.shops`。
这一行是"两个数据源冲突"的唯一答案。

## 十、遗留项的收尾（V12.1）

### 10.1 分店关闭（`closeStore`）

#### 规则设计

| 问题 | 决定 | 理由 |
|---|---|---|
| 总店能关吗 | **不能** | 总店是经营的根，关了游戏没法玩 |
| 店费退不退 | **不退，还倒付清退费** | 已投的装修/库存/招人是沉没成本。若能全额退款，玩家会「开了又关」来试城市 —— 那不是经营决策，是无成本试错 |
| 店长的员工 | **遣散** | 店都没了，店长与员工无处可去 |
| 店长本人 | **撤下，不给补偿** | 店是玩家的，店长领的是「有店可管」的薪酬 |
| 店号 | **重排**（后面店往前移） | 玩家会期望「关掉 3 号店后 4 号变 3 号」 |
| 员工 | **不回总店，直接遣散** | 员工是总公司的，但没工位了 |

#### ★ 关店与「卸任店长」是**不同的两件事**

| | 卸任 | 关店 |
|---|---|---|
| 店 | 还在 | 没了 |
| 员工 | **留下**（他们是总公司的，不是店长的） | **遣散**（没工位了） |
| 店长 | 拿 3 倍日薪补偿 | 不拿补偿（工作没了） |

混为一谈会造成「关店后员工凭空消失」或「关店后员工还在无主的店里」。

#### 店号重排必须同步三处

```
s.stores[].branch        ← 店号
s.staff[].branch         ← 员工归属
s.managers[].branch      ← 店长所在店
s.mgrCand{}              ← 候选池的键（按店号存）
```

漏任何一处都会出现「员工归属一家不存在的店」或「候选池串到别的店」。

**主店被关时**，主店标记必须转移（否则出现「没有主店」的状态）。

#### 二次确认

两端都必须有：H5 用 `confirm()`，Canvas 用自绘的 `MODALS.confirm`。
不是"怕手滑"，而是这个操作**不可逆**（店没了、员工遣散、店费沉没）。

### 10.2 Canvas 端自绘输入

**抖音小游戏端没有输入框**（项目里已明说：「抖音小游戏内没有输入框」）。
所以数值与文本输入必须自绘：

| 输入 | 形态 | 理由 |
|---|---|---|
| 金额（注资/提现） | **数字键盘**（0-9 / 退格 / 确定 + 4 个快捷金额） | 金额是连续数值，循环选择（+100/+500/+1000）覆盖不了"我想提 327 元" |
| 店名（改名） | **候选名循环**（城市名 × 8 种后缀） | 中文输入法在 Canvas 上做不了（没有键盘），"轮候选"是触屏上唯一可行的形态 |

顺带加了 `MODALS.confirm`（通用确认弹窗），关店确认与其他未来场景都能用。

### 10.4 店铺级升级（`STORE_UPGRADES`）

把 `store.upgrades` 从空占位变成可用的功能。4 项，**每店独立**：

| id | 名称 | 效果 | max |
|---|---|---|---|
| `buzz` | 旺铺招财 | 该店客流 +12%/级 | 5 |
| `team` | 熟练团队 | 该店员工效率 +10%/级 | 5 |
| `sign` | 本地招牌 | 该店可上架 +1/级 | 3 |
| `lean` | 精打细算 | 该店固定开支 −10%/级 | 5 |

#### 为什么必须有

有了 V12 的「每店独立账本 + 独立等级」之后，玩家会自然想「把某一家店做成主打店」——
而没有单店投入的途径，就只能把所有资源平摊给所有店，
「重点培养哪家店」这个决策根本不存在。

#### 与全局升级的分工

| | 全局 UPGRADES | 店铺升级 |
|---|---|---|
| 作用范围 | 所有店一起受益 | **只作用于那一家店** |
| 数值 | 更高（decor 全店 +15%） | 略低（buzz 单店 +12%） |
| 决策含义 | 「连锁总部统一投入」 | 「重点培养某一家」 |

单店效果更弱是**应该的** —— 否则玩家会只买店铺升级，全局升级就没意义了。

#### 成本随店铺等级上浮

`base × mult^lv × (1 + (店铺等级−1) × 0.22)`

大店的升级更贵。这让「先开小店练级再做大店」有策略意义，
也防止玩家把所有店都堆到高等级（那样店铺升级就只是数值膨胀）。

#### ★ 托管店同样吃店铺升级

否则玩家投了升级的托管店反而比没升级的自营店弱，
「托管」就成了纯粹的损失 —— 那个功能也就没有意义了。

#### UI

H5 端默认**收起**（4 项 × 每店 = 页面会很长），点标题才展开；
Canvas 端没有折叠交互，直接列出（卡片高度相应增加）。

### 10.5 留档店长（`formerManagers`）

关店时店长不直接丢弃，而是**留档**到 `s.formerManagers`，
玩家可随时**免费请回**。

#### 为什么

不留的话，玩家关掉一家店就永远失去这个店长 ——
而「关店再开一家、把这位能干的老店长请回来」本该是个有意思的经营循环
（换一个城市用同一位能人）。

#### 规则

- **不额外收费** —— 他本来就是在职时被关停的，
  重新启用是「恢复原职」不是「招新人」，
  收一笔招募费等于为同一份履历付两次钱。
- 仍受「每店至多一名店长」与「店长数 ≤ 店数」约束。
- 启用后从留档列表移除（不能反复启用同一人）。
- id 必须避开现役店长的 id（否则两者撞 id → 加成算两次、工资付两次）。

#### 存档清洗

- 必须是数组（老存档没这字段）
- 字段逐个夹取（脏存档可能塞字符串等级/负工资）
- **不能与现役店长重名同 id** —— 否则两个店长共用一个 id
- 留档数量上限 12（否则脏存档能塞 1000 个，白嫖店长）

### 10.7 这一轮修掉的测试缺陷

| 症状 | 根因 |
|---|---|
| `N2d 客流加成 22% < 20%` 误报 | 断言写死 `< 1.2`，而候选店长是**随机**的（Lv.1~5，加成跨度 1.03~1.32）。抽到 Lv.4/5 就误报 —— **上一轮就存在的 flaky 断言**，只是之前没抽到高等级。改为按设计上限断言（`< 1.35`） |
| `S11q 重新启用收费了` 误报 | 基准现金取在**开店之前**，把开店成本算到 rehire 头上。基准必须在开店后取 |
| `S11k/l 托管店吃效率/开支加成` 失败 | 测试只买了 `buzz` 升级，team/lean 等级是 0 |
| `S11u 存档后升级丢失` 报错 | 那个场景已经关掉了店，升级随店消失（正确行为），断言却去读已不存在的 `stores[1]` |
| `名额 1→2` 失败 | 断言写死了基准店数，但本段之前可能已开过店。改为按「开店后 = 开店前 + 1」断言，**与测试顺序解耦** |

> 最后一条是通用教训：**断言不应依赖测试的执行顺序**。
> 写死绝对值 = 与前面的测试耦合 = 别人加一段测试就会把你的断言搞红。
