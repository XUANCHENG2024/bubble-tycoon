# 伪 3D 改造说明（V15· isometric）

> 适用范围：**微信小游戏版**（`minigame/`）。H5 版是 DOM 渲染，
> 改造成本与收益不成比例，本轮未动。

## 一、为什么只改小游戏版

两端的渲染方式根本不同：

| | 渲染 | 伪 3D 可行性 |
|---|---|---|
| H5（`js/ui.js`） | DOM + CSS（31 处 `innerHTML`） | 只能靠 CSS `transform: rotateX/rotateY` 做**假**斜角，DOM 布局无法做真实的深度排序与遮挡 |
| 小游戏（`minigame/src/ui.js`） | Canvas 2D 逐帧绘制（272 处 `ctx.` / `GFX.`） | 坐标可任意变换，天然适合等距投影 |

所以本轮把伪 3D 落在小游戏版，H5 保持原有观感。

## 二、投影方式

**2:1 等距**（像素游戏最经典的角度），实现在新增的 `minigame/src/iso.js`：

```
世界坐标 (gx, gy, gz)  ──project()──▶  屏幕 (sx, sy)

sx = ox + (gx - gy) * TW/2
sy = oy + (gx + gy) * TH/2 - gz * TZ      其中 TH = TW/2（严格 2:1）
```

反向（拾取用）直接求逆：

```
gx = ((sx-ox)/a + (sy-oy)/b) / 2
gy = ((sy-oy)/b - (sx-ox)/a) / 2        其中 a=TW/2, b=TH/2
```

**为什么选 2:1 而不是 26.57°**：2:1 的主方向落在整数或半整数像素上，描边不糊、低端机不抖；26.57° 会落在无理数上，肉眼可见锯齿抖动。

实测投影↔反投影往返误差 **0.00e+0**（`check-iso.js` ②）。

## 三、深度排序（z-order）

**深度键 = `gx + gy`**。等距里「屏幕 y 大的 = 更靠前」，而 `sy ∝ (gx+gy)`，所以直接用它排。

排序实现是**插入排序 + 复用数组**，不是每帧 `sort()`：

```js
var ISO_STAGE_SORT = isoSorter(48);   // 模块级，只建一次
// 每帧：isoSortReset(清长度，保留数组) → isoSortPush(插入)
```

理由：每帧只有一两个元素的深度会变（顾客进队/出队），数组整体近似有序，插入排序接近 O(1)。实测**单帧 0.072ms（32 元素）**，且稳态**零数组分配**。

## 四、物体高度与阴影

| 元素 | 表现 |
|---|---|
| 工位 | **立方体**（顶面 + 两个侧面），光从右上来 → 右面亮、左面暗 |
| 忙碌状态 | 立方体**更高**（`h*0.62` vs 空闲 `h*0.34`）—— 高度差本身就是状态信号 |
| 顾客 | 竖直矩形 + **椭圆阴影**（等距下圆形地面的投影是椭圆，画菱形会像方块） |
| 地面 | 淡淡的菱形地板 —— 没有地面的等距物体看起来是悬空的贴纸 |

## 五、拾取与碰撞

**仍然给 `GFX.addHit` 屏幕矩形，不用反投影**。三条理由：

1. 反投影只给出菱形的**中心归属格**，点在立方体侧面（屏幕上偏下偏左）会算到别的格子；
2. 命中区必须与**视觉**严格一致 —— 玩家点哪都要有反应，菱形反投影会漏掉边缘；
3. `GFX.addHit` 只接受矩形，菱形要自己写多边形命中，收益不抵复杂度。

**重叠处理**：`hitAt` 是**从后往前找**（后登记优先，已核对 `gfx.js:229`），所以按绘制顺序**正序登记**即可 —— 后画的（更靠前的）先被测到，与视觉遮挡一致。

## 六、边界情况（都是实测抓到的）

| 问题 | 症状 | 根因 | 修法 |
|---|---|---|---|
| **横向溢出** | 小屏上最右工位被裁掉，点不到 | 等距的 x 跨度是 `(cols+rows)×TW/2`，**远大于**矩形的 `cols×TW/2`；而 `clipPush` 只裁垂直方向 | 按跨度反推 `TW`，并按 x 极值居中原点 |
| **原点算错** | 最右工位超出视口 62px | 我按「网格左上角」估 `ISO.ox` 再减 `span/2` —— 但 x=0 的格子**不是最左的**（`(gx=0, gy=rows-1)` 才是最左） | `ISO.ox = 视口左 + TW/2 - minOffset + 跨度/2` |
| **占高算错** | 最后一个工位落在可滚动范围外 | 矩形假设「最后一个 = 最靠下」，等距下**不成立**（9 工位排 4 列时 `si=7` 比 `si=8` 更靠下） | 遍历取**真实最大深度** |
| **选列判据过时** | 列数选错 | `pickStationGrid` 仍用矩形占高公式 | 改成同款等距公式 |

## 七、性能

- **不逐帧重建排序**：`isoSorter` 复用数组，稳态零分配。
- **绘制开销**：每个工位多画 3 个面（顶 + 两个侧），9 工位实测**单帧 0.49ms**（`check-iso-stage.js` ⑤，含完整 120 帧统计）。
- **尺寸自适应**：`TW` 由可用宽度反推，夹在 `[44, 76]`。下限 44 是刻意选的 —— 实测小屏 20 工位时 `needTW` 只有 30~34，硬压会让 emoji 与进度条挤在一起看不清；宁可让区域可滚动。

## 八、玩法与输入零改动

**引擎（`js/engine.js`）、玩法数据（`js/data.js`）、关卡、数值、action 全部没动。**
数据结构也不变（`sim.stations` / `sim.queue` 照旧），只是把「矩形网格 + 矩形卡片」换成「菱形地面 + 立方体工位」。

`check-iso-stage.js` ④ 用 `git diff` 守这条红线：**一旦有人顺手改了引擎，这个检查立刻报错**。

## 十、已知限制

- **jsdom 没有布局引擎**，真实溢出与遮挡仍需真机验证。
- 等距下相邻工位的**矩形命中区可能轻微重叠** —— 靠「后登记优先」保证观感一致，但理论上存在 1~2px 的歧义区。
- 队列沿斜边排，**人数多时斜带会变长** —— 沿用原来的「最多 3 排」策略兜住。
