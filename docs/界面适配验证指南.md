# 界面适配验证指南（V20.8）

> 本文覆盖**多分辨率预览**（自动化）与**真机调试**（手工）两条路径。
> 前者可随时跑，后者是上架前必须做的。

> ★ **V20.8 变更摘要**：

## 一、自动验证（一条命令）

```bash
node tools/diag-canvas-layout.js        # 布局诊断（11 设备 + 横屏专项）
node tools/test-text-truncate.js        # 文本截断专项（35 项）
node tools/test-text-scale.js           # 字号缩放专项（86 项）
node tools/check-android-res.js         # Android 资源 + 图标密度（60 项）
```

**它做什么**：在 11 种真实设备尺寸下**真实渲染**整个 UI，拦截每一次 Canvas 绘制调用，
然后检查三类问题：

| 判据 | 抓什么问题 | 为什么可靠 |
|---|---|---|
| **横向越界** | 元素超出左右边界 | 横向**没有滚动条**，超出就永远看不到 |
| **固定元素被安全区遮挡** | 底部按钮被 Home 指示条盖住 | 只检查**裁剪区之外**的元素（面板内容会滚动，被裁掉是正常的）|
| **文字被截断** | 容器太窄导致信息丢失 | 看文本是否以 `…` 结尾 |

**覆盖的设备**：

```
小屏 320×568 · 主流 375×667 · 大屏 414×896 · 刘海 390×844
折叠 344×882 · 平板竖 768×1024 · 平板横 1024×768 · 折叠内屏 673×841
手机横 844×390 · 手机横 736×414 · 平板横 1180×820
```

还会输出**布局度量表**（每种设备的 HUD 高度、内容宽、缩放系数）、
**横屏两栏断言**（确认横屏时标题页真的走了两栏版，而不是碰巧没溢出）、
**横屏 × 13 种弹窗 / 引导层 / 结算页**的越界与遮挡检查、
以及**左右安全区（横屏刘海）**的避让断言。

### ★ 两套专项测试为什么必须存在（V20.8 新增）

| 测试 | 抓什么 | 已经抓到的真实缺陷 |
|---|---|---|
| `test-text-truncate.js` | `GFX.text()` 的 `maxW` 截断路径 | **3 个**：`maxW=0` 完全不截断 / 省略号预留顺序错误导致词边界被破坏 / 截断三步顺序倒置 |
| `test-text-scale.js` | `FS` getter 与 `setTextScale` | 确认 361 处 `FS.xs` **真的**跟随缩放（V20.7 的 `L.scale` 就是"看起来适配、实际无效"）|

★ V20.7 改过截断算法却**从未被任何测试覆盖** ——
这正是「看起来做完了、实际没测过」的典型。V20.8 补上。

### 局限（必须知道）

★ 这是**几何检查**，不是像素检查：
- 它能证明「元素没越界、没被遮挡」，**证明不了「好看」**
- 它不检查颜色对比度、不检查视觉层级、不检查动效
- ★ 布局是否真的「居中好看」，必须**人眼看**

## 四、Android 侧配置说明

### 4.1 沉浸式与 edge-to-edge（★ V20.8 已改）

`app/android/.../MainActivity.java`：

```java
WindowCompat.setDecorFitsSystemWindows(getWindow(), false);   // 内容全屏
controller.setAppearanceLightStatusBars(false);
controller.setAppearanceLightNavigationBars(false);
getWindow().setStatusBarColor(Color.TRANSPARENT);             // 透明系统栏
getWindow().setNavigationBarColor(Color.TRANSPARENT);
```

★ **V20.8 的关键改动：不再 `hide(systemBars())`**。

V20.7 用的是「隐藏系统栏 + 上滑唤出」，看起来很沉浸式，但有个**致命副作用**：

> ★ **系统栏一旦隐藏，`WindowInsetsCompat.Type.systemBars()` 的 inset 恒为 0** ——
>   因为系统栏已经不占位了。
>   ★ 而手势条 / Home 指示条**仍然物理覆盖**屏幕底部。
>   ★ 结果：两条读取路径（原生 inset 与 CSS env()）**都拿不到真实值**，
>   底部按钮照样被盖住 —— 而且是静默失效，看不出任何异常。

V20.8 改为「**系统栏保持可见但透明**」：
- 视觉上仍然是沉浸式（内容延伸到栏下，栏本身透明）
- 但 inset 是**真实可读**的
- 安全区数值由新插件 `AppInsetsPlugin` 提供

★ **为什么不用 `FLAG_FULLSCREEN`**：它只隐藏状态栏，导航栏还在。
而 targetSdk 35 → **Android 15 强制 edge-to-edge**，系统栏一律覆盖在内容上。

### 4.1.1 ★ 安全区的正确来源（V20.8 新增）

`app/android/.../AppInsetsPlugin.java`：

```java
Insets bars   = insets.getInsets(WindowInsetsCompat.Type.systemBars());
Insets cutout = insets.getInsets(WindowInsetsCompat.Type.displayCutout());
// 取 max，再 ÷ density 换成 CSS px
```

| 来源 | 覆盖情况 | 结论 |
|---|---|---|
| CSS `env(safe-area-inset-*)` | **iOS / 桌面浏览器可靠；Android WebView 上 Chromium < 140 在 edge-to-edge 下静默返回 0** | ★ 不可作为 Android 的唯一来源 |
| `@capacitor/status-bar` | 只有 `statusBarHeight`（**仅顶部**），无底部导航栏、无刘海 | ★ 不够用 |
| `@capacitor-community/safe-area` | 需额外依赖；作用是给旧版 WebView 打 padding，会让 WebView 整体内缩 | 与「Canvas 自己避让」冲突 |
| **`WindowInsetsCompat`（本插件）** | 系统栏 + 刘海 + 旋转实时值 | ★ **采用** |

★ JS 侧读取优先级（`minigame/src/platform.js` 的 `safeInsets()`）：
**原生推送值 → env() 探针 → 全 0**。

★ 原生是「推」的（`window.__APP_INSETS`），因为 `PLAT.info()` 是同步函数，
而 Capacitor 插件调用**永远是异步的** —— 只靠 JS 主动拉，首帧必然算出 inset=0，
视觉上会「跳一下」。页面就绪后还会再异步补拉一次作为兜底。

### 4.2 屏幕方向

`AndroidManifest.xml`：

```xml
android:screenOrientation="unspecified"
```

★ 从 `portrait` 放开的原因：
- Google Play 对**大屏适配**有要求，锁竖屏影响商店评分与推荐
- 平板用户横持是常态
- ★ 旋转后的拉伸问题已在 Canvas 版修好（resize 处理）

★ 用 `unspecified`（跟随系统）而不是 `sensorLandscape` ——
后者会**强制横屏**，竖着拿手机的玩家会晕。

### 4.3 resize 处理（Canvas 版的关键）

Android 的 `configChanges` 含 `orientation|screenSize` →
**旋转时 Activity 不重建**，只 resize WebView。

而 Canvas 版原先只在 `boot()` 时算一次 `CW/CH` →
旋转后 canvas 被浏览器拉伸到新视口，内部坐标还是老的 → **画面变形**。

现在 `main.js` 监听三种信号：

```js
window.addEventListener('resize', handleResize);
new ResizeObserver(handleResize).observe(canvas);
window.addEventListener('orientationchange', handleResize);
```

`handleResize()` 会：
1. 清安全区缓存（旋转后刘海/指示条位置会变）
2. 重算 `CW/CH` 与安全区
3. 重建 canvas 尺寸与 DPR 变换
4. 立刻重绘一帧

★ **代价**：重设 `canvas.width` 会清空画布 → 一帧闪白。下一帧 rAF 会立刻补上，
肉眼几乎看不出。若要彻底消除，可用双缓冲（离屏 canvas 交替）。

## 五、如何改布局（给后续维护）

### 布局的唯一真源

```js
minigame/src/ui.js → layoutOf(W, H)
```

它返回：

| 字段 | 含义 |
|---|---|
| `W` `H` | 视口尺寸 |
| `hudH` `tabH` | HUD / tab 栏高度（已含安全区上边距）|
| `bodyY` `bodyH` | 内容区顶与高度（**已减掉底部安全区**）|
| `padTop` `padBottom` | 安全区上下边距 |
| `scale` | 缩放系数（窄屏 0.94~1.10，宽屏 1）|
| `wide` `short` `foldable` | 视口分类 |
| `contentX` `contentW` | 内容区（宽屏时居中限宽 640）|
| `padX` `innerW` | **内容区内的左右边距与可用宽度** ← 各面板用这个 |

### ★ 各面板应该用 `L.padX` / `L.innerW`，不要用 `W - 32`

```js
// ✘ 错：宽屏上会铺满 992px，文字一行太长
var x = 16, w = W - 32;

// ✔ 对：限宽居中后自动正确
var x = L.padX, w = L.innerW;
```

### ★ 绘制与命中必须用同一个 x

```js
GFX.button(ctx, x, y, w, 44, '…', {...});   // 画在 x
GFX.addHit(x, y, w, 44, 'act', ...);        // ★ 命中也必须在 x
```

★ `GFX.addHit` 记录的是**绝对坐标**，`ctx.translate` 对它无效 ——
所以**不能用平移上下文来做居中**，必须改坐标本身。

### ★ 字号：`FS.key` 本身就会跟随缩放（★ V20.8 已反转上一条）

```js
text(ctx, '…', x, y, { size: FS.sm });        // ✔ 跟随缩放
text(ctx, '…', x, y, { size: fs(L, 'sm') });   // ✔ 等价（兼容旧调用点）
```

★ **V20.8 的改动**：以前 `FS.xs` 是固定 10px，只有 `fs(L,'xs')` 才乘 `L.scale`。
但全仓有 **361 处** `FS.xs` 直接读取、只有 36 处用 `fs(L,...)` ——
`L.scale` 几乎没效果，**「看起来做了适配」比「没做适配」更糟**。

现在 `FS` 是一个 **getter 令牌表**：

```js
Object.defineProperty(FS, k, {
  enumerable: true, configurable: true,
  get: function () { return Math.round(FS_BASE[k] * _textScale * 2) / 2; },
});
```

- `layoutOf()` 每次布局调 `GFX.setTextScale(scale)` → **361 处全部跟随**，改一处生效全部
- `fs(L, key)` **不再乘第二次**（否则 320 屏上 `10 × 0.94 × 0.94 = 8.8`，中文直接糊了）
- 缩放系数非法（0 / NaN / >3）**一律退回 1** —— 缩放变 0 会导致全屏文字消失，那是灾难级故障
- `tools/test-text-scale.js` 专门守这条不变量（86 项断言）

★ **新增代码请直接用 `FS.key`**，`fs(L,key)` 仅为兼容既有调用点而保留。

## 七、★ 真机必查项补充（V20.8）

前面 3.3 节的清单是通用项。V20.8 引入了原生安全区通道，
以下几项**只能靠真机验证**，自动化检查不到：

| # | 检查 | 怎么确认 | 期望 |
|---|---|---|---|
| 1 | **原生 inset 是否真的取到值** | Chrome `chrome://inspect` → Console 执行 `window.__APP_INSETS` | 返回 `{top:…, bottom:…, ok:true}`，且 `bottom` **大于 0**（手势条机型上通常是 24~48） |
| 2 | 底部按钮是否被手势条盖住 | 看「开门营业」/「暂停」按钮 | 完整可见、**能点到**（看得见点不到 = 仍被盖住）|
| 3 | 刘海屏顶部 | 灵动岛/挖孔机型上看 HUD 第一行 | 数值胶囊不被挖孔压住 |
| 4 | 横屏侧边刘海 | 横屏时看左右两侧 | 内容不被侧边挖孔压住（V20.8 新增 `insLeft/insRight` 避让）|
| 5 | 旋转后 inset 是否刷新 | 旋转后 Console 再读 `window.__APP_INSETS` | 数值随新方向变化 |
| 6 | 图标是否被系统裁圆 | 看桌面图标 | 圆形图标**居中、不被切边**（Android 8+ 自适应图标）|
| 7 | 图标是否清晰 | 在 xxhdpi 设备上长按看图标 | 边缘不糊、不锯齿 |
| 8 | 320 宽小屏字号 | 小屏（或 DevTools 320×568）| 中文**不糊**（字号应为 9.5 而非 8.8）|
| 9 | 长文本截断 | 看配方名/员工名 | 省略号在**空格边界**、不出现半个单词 |

★ 第 1 项是**本轮最关键的验证** —— 它是「Android 安全区是否真的修好了」的**单一真相来源**。
如果 `__APP_INSETS.ok` 是 `false` 或 `bottom` 是 0，说明原生通道没生效，
其余检查都失去意义。
