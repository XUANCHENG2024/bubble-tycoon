## 二、三个真实缺陷

### ① 三条每日合同**永远不可能完成**（`js/data.js` + `js/engine.js`）

**证据**：`c_cheap` / `c_premium` / `c_nolost` 的 `check` 读 `m.avgCap` / `m.avgFloor` / `m.lostCap`，
而 `contractMetrics()` 从来没有产出过这三个字段。
JS 语义下 `m.avgPrice <= undefined` **恒为 false**。

**影响**：10 条合同里 3 条是死规则，按每天随机 1 条算，**28.9% 的日子**玩家拿到一个注定失败的任务，
失败还要扣 3~4 点口碑（口碑直接决定次日客流）。界面上完全看不出来：目标正常显示、进度正常算，只是永远不"达成"。

**改法**：阈值显式登记在合同上（`avgCap: 28` / `avgFloor: 26` / `lostCap: 2`），
`contractMetrics()` 从**当前合同**取，缺省 ±Infinity（没设阈值的合同不会被"默认 0"误杀）。

**验证**：新增 `tools/check-contract.js`（18 项）——每条合同喂一份"完美的一天"必须能判达成；
另有反证（单价 ¥40 时必须判失败）。已接入 CI。

---

### ② 托管分店**完全不吃玩家的定价**（`js/engine.js`）

**证据**：托管店每日营收里写的是 `recipeById(rid).price`（**出厂价**），
而自营店走 `priceOf(s, rid)`（基准价 × 玩家倍率 + 招牌加价）。

**影响**：玩家把招牌提价 20%、或整体倍率调到 1.3，**自己看的店多赚，托管的分店一分不涨**。
而托管恰恰是玩家不亲自盯的那家店——最应该吃定价策略的红利，却对定价免疫。

**改法**：客单价改走 `priceOf()`，同时引入 `priceDrag = clamp(1 − (avgRatio − 1) × 0.35, 0.55, 1.10)` 扣量。
只换价格不扣量等于"倍率拉满就是无风险套利"（分店客流本来不受价格影响）。
★ **ratio = 1.0 时 priceDrag = 1，行为与旧版逐字节一致**——不动定价的玩家不会感到任何变化。

**验证**：`check-balance` / `e2e-flow` / `minigame-smoke` 全绿；AI 不用分店，故 sim 侧无漂移。

---

### ③ 小游戏端"达成"听起来像"点了个按钮"（`minigame/src/platform.js`）

**证据**：分流规则是纯频率硬切 `freq >= 850 → tap`。而代码里 48 处 `beep()` 中，
达成类反馈大量用 880 / 980 / 1175 / 1405Hz —— **全部落进 tap（0.06 秒点击声）**。
`main.js` 里还写着注释"三音上行是本作最高音档，刻意区别于普通成功的 760Hz"，
真机上那三个音都是"嗒"。

**改法**：分流改为**语义优先、频率次之**（`kind` 决定意图，频率只在同一意图内分强度），
新增 `up2.wav`（三音上行）与 `ach.wav`（四音上行），3 个文件 → 5 个，体积 17KB → 65KB。
里程碑三连音收敛成单次 `beep('ach')`（原来三个音轨会互相盖住）；成就补上音效（此前只放彩纸）。

**验证**：新增 `tools/check-audio.js`（30 项）——文件齐全、WAV 头合法、时长区间、体积预算、
映射表每个 key 都指向存在的文件、**旧的 `freq>=850→tap` 规则已被移除**。已接入 CI。

## 三、两套从未标定过的数值

### 三档难度目标（`js/data.js`）

**证据**：60 局实测（bp=0 / 随机策略卡）——三档的终局净资产几乎一样：

| 档 | 平均 | 中位 | p75 |
|---|---|---|---|
| easy | 42699 | 44725 | 48820 |
| normal | 42034 | 43662 | 47596 |
| hard | 39445 | 38451 | 45886 |

而旧目标 easy **58000** / normal 47000 / hard **54000** ——
easy 的目标比 hard 高 7%，锚点还是实测的 1.28 倍 ⇒ **一局都通不了**（0/18）。
只有 normal 是认真标定过的。

**改法**：目标改为 **40000 / 44000 / 48000**，锚点按各档**自己**的实测逐日曲线 × (新目标/实测终值)。
不共用一套比例：三档增长形状不同（easy 前快后慢、hard 全程平缓），共用比例必然在某档上过松或过紧 —— 旧值出错正是这个方式。

**改后（N=22/档，`cards=none` 基线 —— 见下方"标定口径"）**：

| 档 | 目标 | 过关率 | 完成度 | 分布（p25 / 中位 / p75） |
|---|---|---|---|---|
| easy | 42000 | **95~100%** | 117~123% | 45642 / 48384 / 53117 |
| normal | 45000 | **50~73%** | 100~107% | 43028 / 45030 / 47977 |
| hard | 47000 | **20~32%** | 90~93% | 40827 / 43689 / 47246 |

★ 区间而不是单值，是因为 22 局/档的抽样噪声有 ±10pp（同一份代码，normal 在不同批次里
50% 与 73% 都出现过；hard 在 47k 目标下也见过 14% 与 32%）。
**不要拿单批数字去微调目标** —— 这正是本轮差点犯的错（见下）。

> **标定口径（比数值本身更重要）**
>
> 1. **基线 = 不抽策略卡（`--cards=none`）。** 本轮已确认策略卡是负期望
>    （不拿卡一律更好），理性玩家的最优解就是"都不要"，所以"玩家实际会打出的成绩"
>    必须按 none 算。用 random 当基线会把目标整体定低 —— 同一份代码，
>    normal 的过关率是 33%（random）vs 73%（none）。
> 2. **验收看过关率**（过线局数/总局数），不看"平均净资产/目标"。
>    后者是完成度，两者会给出**相反**的结论：旧 easy 完成度 81%，过关率却是 0%。
> 3. **顺序固定：先修 bug → 测基线 → 再调目标。** 本轮先修了合同死规则（它一直在扣口碑、
>    压低所有人的成绩），如果先调目标再修 bug，修完之后目标立刻失准。
>    本轮过关率从"easy 0% / hard 0%"变成现在这样，有一半是 bug 修复的功劳，不是调数值的功劳。
> 4. **样本不够不要下结论。** hard 曾有一次独立采样 0/12，看着像"不可能"；
>    合并 56 局后是 11%。按 13% 的期望值，12 局全灭的概率约 19% —— 属于正常波动。

→ 目标金额递增（42k < 45k < 47k）、过关率递减，两条轴同时单调。
⚠️ 不能反过来给 hard 设更低目标来"保证能通"——那会让玩家看到"地狱模式目标比简单模式低"，比现在更荒谬。

### 进度条刻度（`MILESTONE_RATIO`）

固定写死 `[0.09, 0.17, 0.28, 0.42, 0.58, 1.0]`，而 normal 的真实锚点占比是
`[0.105, 0.202, 0.334, 0.539, 0.80, 1.0]` —— 第 5 个刻度**错位 22pp**：
玩家看到刻度已过，判定还没到。

第一次修的时候我把它改成了算好的常量 `[0.105, …]`，但那只把"错位"换成了"此刻恰好对齐"：
下一次谁调 normal 的 goal，刻度立刻再次脱节，而且**不会有任何测试变红**（长度没变、数值看着也合理）。
最终改成**从 `STAGE_GOALS.normal` 派生**：

```js
const MILESTONE_RATIO = STAGE_GOALS.normal.map(v => v / DIFFICULTY.normal.goal);
```

调 goal 不必重算刻度，两版 UI 一行都不用改；`check-parity-goal` 守住 ≤1.5pp。

## 四、性能：研发页 −67% 绘制调用

**测量**（`tools/diag-canvas-layout.js` 现会逐面板打印绘制调用数，375×667）：

| 面板 | 改前 | 改后 |
|---|---|---|
| lab（研发） | 538 | **178** |

**根因**：面板是**全量绘制**（没有视口剔除）。研发树 57 个节点 + 配方 60+ 款，
玩家一屏只看得见 ~9 行，其余 80% 的 `fillRR`/`fillText`/`button` 画完就被 `clipPush` 丢掉。

**改法**：`gfx.js` 新增 `visibleY(y, h)`——与当前裁剪区求交，不相交就整行跳过。
判据故意宽松（相交即算可见，留 1px 余量），宁可多画一行，也不能让滚动边缘出现"半行被吃掉"。
★ `y += 行高` 必须在 `continue` 之前：行高是绝对累加，跳绘制不能跳布局。
★ 命中区不用单独处理：`addHit` 本来就会把命中区裁到 clip 内，整行在视口外时它登记出来的矩形会被裁没。

**验证**：`diag-canvas-layout` / `diag-fit-audit` 均 0 问题（无内容缺失、无越界）；
`check-iso-stage` / `check-deadbtn` / `check-ui-spec` 全过（可点性未变）。

## 五、体验：流失从"一个数字"变成"一条行动"

**证据**：结算只写「流失 12 位」，最多补一句缺料/嫌贵。
玩家知道丢了 12 个人，但**不知道该改什么**——四类流失的修法完全不同：

| 流失类型 | 该做什么 |
|---|---|
| 等太久 | 加出杯位 / 升效率 / 招人 |
| 嫌太贵 | 调低倍率 / 上架便宜款 |
| 没座位 | 升装修扩队列 |
| 缺料 | 备货 |
| 没排到（打烊清场） | 产能不足 |

**改法**：引擎新增 `waitLost` / `fullLost` / `closedLost` 三个计数（`priceLost` / `stockout` 已有），
新增 `lostBreakdown(r)` 统一产出「按数量降序、只留非零项」的归因表，两版 UI 共用（避免口径漂移）。
结算显示「流失 12（等太久 8 · 嫌贵 3 · 没座 1）」+「主因是『等太久』—— 加出杯位 / 升级效率 / 招人」。

**验证**：`dom-smoke` / `browser-smoke` / `minigame-smoke` / `diag-fit-audit`（新增一行文字未撑破面板）全过。

## 六、测量工具本身的三处修正

数值结论的可信度取决于测量口径。这轮修了三处会**误导后续所有平衡工作**的口径问题（`tools/sim.js`）：

1. **「达标率」其实不是达标率** —— 原来打印的是 `avg / goal`，那是**平均完成度**。
   实测反例：easy 报「达标率 90%」，但 18 局一局都没到 58000（中位 44725）。
   现在拆成两个数字：`达标 N/M 局（x%）` 与 `完成度 y%`。
2. **「破产局次」混进了别的东西** —— 原来 `log.some(x => typeof x === 'string')`，
   把「无法开门」也算成破产，于是出现「达标 6/6（100%）⚠️ 破产 3」这种自相矛盾。
   现在分开报：`破产 1,3 · 无法开门 5`。
3. **提前中断的局被算进达标** —— 它在 Day N 就停了，净资产是"半局成绩"，
   拿去和 30 天目标比会高估达标率、污染平均值。现在达标率只按**完整局**算。

## 七、被证伪 / 未落地的提案

| 提案 | 结论 |
|---|---|
| 静止时降到 30fps | **不做**。掉帧的代价是漏重绘 —— 玩家会看到"点了没反应"，而这个项目的历史缺陷清单里「点击无响应」出现过不止一次。收益（省电）远小于风险。 |
| 策略卡从「每 3 天一次」改到「每 2 天一次」 | **暂缓**。卡片在 Day 18 之后就抽完了（每 3 天 × 最多持 6 张），后 40% 局没有 build 决策——判断成立。但**顺序不能反**：先修卡池质量，再改频率。理由见下一条。 |
| 营销费"沿用上次" | **暂缓**。能省 30 天 × 2 次点击，但要改两版 UI 的输入态；本轮已改 4 处 UI，避免一次改太多。 |
| 成就分级（铜/银/金）、结算评分卡 S/A/B/C | 未做。属于新增反馈层，各 0.5~1 天。 |

### 已核实但本轮**刻意没改**的数值问题

这些不是"没发现"，而是"改了就必须重跑另一整套标定"。逐条记录，供下一轮用：

| 问题 | 证据 | 为什么本轮不动 |
|---|---|---|
| **成就现金占净资产约 48%**（Day1 就占 44~58%，等于开局资金翻倍） | 单局抽 2 局累计成就现金 11350 / 23350 | 这会直接改变资金曲线与开局节奏。刚把三档目标标定完，再动收入端就要连目标一起重标 —— 一轮只该动一头。 |
| **「外卖接单」边际产出接近 0**（自营局 4637，封禁该升级后 6360） | 但样本差在噪声内（±3~5pp），**不能断言负收益** | 只能确认"ROI ≈ 0"，不能确认"负"。要定性需要 n≥60 的同种子 A/B。 |
| **「员工培训」被「极速封口机」严格支配** | `serviceTimeOf` 里两者同除一个分母：speed 20%/¥200 vs training 12%/¥320，且 training 的涨价系数更高（1.68 > 1.55） | 严格支配是**静态可证**的（不依赖采样），但修法会改早期 build 顺序，属于设计决策而非 bug 修复。建议下一轮单独做。 |
| **冷链仓库（storage）是全局瓶颈**（ROI 6.77，其余 1.x~2.x） | 所有料共用一个 `storageCap`，产能排序又依赖它 | 它是**设计上刻意**的瓶颈（逼玩家在仓库与设备间取舍）。是否该有第二条扩容路径需要设计判断。 |
| **策略卡约 10/12 为负期望**，加上"都不要"按钮 ⇒ 理性玩家永远跳过 | **已确诊**（三口径实测，见下表） | 确诊 ≠ 该现在改。12 张卡要逐张标定，本轮已经动了目标/合同/分店三处数值，再动卡池会让所有结论互相污染。 |

## 八、仍需人工确认的问题

1. **难度目标是不是"对真人合适"** —— 全部数据来自脚本 AI（2.5 次/秒点击、不用策略卡、无声望加成）。
   真实玩家会用卡、有开局基金、有招牌继承，实际达标率应高于此。**建议真机各打 3 局三档**，
   若 easy 低于 70% / normal 低于 30%，说明 AI 比人强，目标还要再降一档。
2. **hard 前 3 天的锚点是否过紧** —— 按各档自身曲线缩放后，hard 的 D5 锚点 4700 对实测中位 3824 是 1.23 倍，
   约 1/4 的局能拿到第一个「声望 +1」。若你希望 hard 也能稳定吃里程碑，这个值该降到 4200 左右。
3. **分店定价的弹性系数 0.35** —— 选它是因为 ratio=1 时行为与旧版完全一致（安全边界），
   但"提价 30% 掉量 10.5% 净赚 16%"是否合理，没有实测数据支撑，只有一次手动验算。
   **需要一局真实多店存档验证**：提价后分店营收是否如预期上升、且不至于变成印钞机。
4. **新增音效的主观听感** —— `ach.wav` 是四音上行（E5-A5-C6-E6），
   在手机外放上会不会太尖，需要真机听。文件头、时长、体积都已断言，唯独"好不好听"没法断言。
5. **iOS 端尚未编译验证**（无 Mac）。音频走同一套 `createInnerAudioContext` 分支，理论上一致。
6. **策略卡是不是真的失效了** —— 本轮**已确诊：是**。
   `node tools/sim.js 8` 三口径（每档 8 局）的**完成度**：

   | 档 | none（不拿卡） | first（永远拿第一张） | random（随机拿一张） |
   |---|---|---|---|
   | easy | **133%** | 124% | 125% |
   | normal | **106%** | 96% | 100% |
   | hard | **89%** | 84% | 87% |

   **不拿卡一律更好**，且 normal 档偏差 **10pp**、easy 档 8pp —— 都越过了项目自己定的
   「三口径应当接近（±8pp 内）」红线。项目文档里"12 张卡张张有得有失、漂移 ≤2pp"
   的结论在当前版本**已经失效**。
   ⇒ 这意味着一个"每 3 天一次、最多持 6 张"的门面系统，对理性玩家来说是**纯负收益**，
   「都不要」按钮反而是最优解。下一轮的第一优先级应当是重标这 12 张卡（或把成本侧整体下调），
   而不是去增加抽卡频率 —— 频率再高，卡更负也没人拿。

## 十、三方会审后的裁决（2026-10-28 收尾）

三位角色在收尾阶段各自提出了修正。这里逐条裁决，结论也回写进了代码注释与工具输出。

### 裁决 1：不再微调 goal（不采纳 43000/44000/46500）

两批数据对 normal 的估计差了 **30pp**（我 n=22 得 50~73%，对方得 80%），
说明样本还不足以支撑 ±1000 级别的微调。且 n=3 时过关率的 95% 区间宽达 **±53pp**
（`sim.js` 现在会直接把这个数字打出来）。
⇒ 保留 easy 42000 / normal 45000 / hard 47000；先统一测量口径（n≥100）再谈调值。

**更重要的是**：三位一致认为"末段空转"**不是 goal 能治的** ——
把目标往后推只会降低过关率，不会让 Day 19~30 多出决策。
所以这里再花时间调数字是浪费，真正该动的是下面裁决 3。

### 裁决 2：成本杠杆本轮不动（已确认是真问题）

`costMult` 全仓只有 5 个使用点，**全部是一次性投入**：
招人费、研发、升级、开店、招募店长。原料价与工资**一分没涨**。
所以 hard 的"+15% 成本"实际是"+15% 投资门槛"，而一次性成本会随时间摊薄 ——
这解释了为什么 hard 与 normal 的终局净资产在统计上不可区分
（43689 vs 45030 中位，同一区间）。

修法（下一轮）：给 hard 加 `cogsMul`（原料 ×1.20）与 `wageMul`（工资 ×1.10）——
**这两个才随时间累积、才是真正的难度杠杆**。

⚠️ 但这会和 goal 标定互相牵连：hard 变难 → 过关率掉 → 目标要不要降？
而目标一降就可能低于 normal，破坏"地狱目标更高"的直觉。
**这是个设计决策，不是 bug 修复**，必须单独一轮，并先定"目标是否允许低于 normal"。

### 裁决 3：末段空转的根因是"没有值得买的出口"（三方独立收敛）

三条互相印证的证据：

| 证据 | 来源 |
|---|---|
| 模拟里分店营收 **恒为 0%**（AI 开了店但不派人） | 数值角色 + 我实测（`sim.js` 现已直接打印这条警告） |
| 研发页内容 8168px、可视 710px，但**命中区只有 13 个** —— 页面长 11 倍，能点的一样多 | 渲染角色 |
| Day 19~30 无新系统、仅剩价格轴 | 玩法角色 |

⇒ 下一轮第一优先级：**修"值得买的扩张出口"**（分店/托管要能真赚钱），
而不是继续加目标、加卡、加锚点。

### 裁决 4：`tools/` 可以改，但本轮不改 AI 决策行为

`ai-shared.js` 让 AI 开店却不派人，导致分店 0 营收 —— 这是**测量缺口**。
但改 AI 会第三次刷掉刚建立的口径（本轮已刷两次）。本轮只做两件事：
1. `sim.js` 打印「分店覆盖 0/N 局」警告，让盲区自曝；
2. `sim -v` 的逐日表原来「卖出/流失」两列是 `undefined`（行里没记这两个字段），已修。

下一轮再改 AI 派人逻辑，并补**非采样断言**：「开了分店必须有人」
（比"营收 > 0"稳定得多 —— 营收受随机客流影响，会变成偶发红灯）。

### 裁决 5：策略卡要换轴，不是调数值

数值角色的推导：场内有 N 个出杯位做并发服务，顾客等位有耐心上限，
**加客流在产能受限时等于加流失**；而 hard 的 traffic 0.90 反而让流失更少、口碑更高
（实测 24% vs easy 36.4%，口碑 90 vs 59）—— **难度杠杆的方向是反的**。

⇒ 卡池改造方向：把"客流 +X%"换成"单位时间吞吐 +X%"或"客单价 +X%"，
并把"等位耐心 +X"提为主轴。约束：**12 张卡的 id 不可改**
（`STRATEGY_CARD_INDEX` 与存档里的已持卡都按 id 引用），只能替换 `name/desc/eff`。

### 顺序（下一轮的唯一正确顺序）

```
① 先修值得买的出口（分店/托管产出） + costMult 作用到经常性成本
② 修正 difficulty 杠杆方向（easy 减 traffic 加 cash；hard 加 traffic 加 cash）
③ 统一测量口径：n≥100，CI 判「完成度」，设计验收判「过关率」
④ 最后才复测 goal —— 前三步做完，目标数字大概率又要动
```

第 ④ 步放在最后，是因为前三步都会改变净资产分布；**先调目标再改机制，
等于用一把会变的尺子量东西**。

## 十一、收尾更正（必须留档，否则下一轮会踩同一个坑）

### 更正 1：分店"营收恒为 0"是**错的**

我在 `sim.js` 里加过一条告警「分店营收 0/N 局」。**这个判断错了**：

⇒ 附带确认：自营分店并非"无收益"，但它的收益**同时受主店备货约束** ——
   分店员工会吃主店的库存，所以"开分店"在缺料严重的局面下是**需求侧 +N、供给侧不变**，

### 触底板：从常量改为判据（这条修法本身值得复用）

固定 `max` 必然错，因为触底级随团队成长移动。实测（从 L=0 扫）：

⇒ easy 到 D30 只差 4 级就触底，而界面能卖到 100 级 —— **玩家可买到 24 倍于有效量的死货**。
现在的修法：`upgradeSaturated()` 每次算"再升一级是否还更快"，并在卡片上写

让刚标定的目标再次失准。

### 一个必须正视的结论：easy 目前**不宽松**

`--cards=none --buy=autoFill`，n=20/档，目标统一 50000：

| hard | **75%** | 0 | traffic 0.90 反而更稳 |

⇒ **难度阶梯目前是反向的**。根因不是目标值，是 easy 的方差与破产率。
明确不做的事：把 easy 目标再调低 —— 那只会让"已经 85% 的档"变成 95%，
而破产率一点不动。**要修的是 σ，不是 μ。**

|---|---|---|---|---|
| 现状 + 强制开店 | 51296 | 65% | 3/20 | −17.3% |
| 客流 20% + 库容 300/店 | 56906 | 85% | 3/20 | −8.2% |
| **客流 20% + 库容 500/店** | **59686** | **90%** | **0/20** | **−3.8%** |
| 客流 0% + 库容 500/店 | 52287 | 70% | 1/20 | −15.7% |

⇒ +300 只把惩罚减半，+500 才到接近中性且**破产归零**；
剩余 −3.8% 全部来自固定成本（upkeep ¥100/天 + 工资）——**不建议为转正去动 upkeep**，否则分店变成无脑必开。

**一条必须更正给全队的规律**：我们之前都说"客流 +X% 永远是惩罚"。
实测把它砍到 0 之后结果反而更差（−15.7% vs −3.8%）：**客流加成本身约值 +12pp，只是需要库容兑现**。
> 正确表述：**客流是"条件性奖励"，条件由库容给出。**
> 库容不足 → 客流是惩罚（−17pp）；库容充足 → 客流是奖励（+12pp）。
⇒ 影响：① 卡池里 traffic 卡的正确约束是"必须同时把库容补到阈值"，不是"给一点产能"；
② 难度设计里"降 traffic = 变简单"只在库容不足时成立，库容修好后会反转。

**为什么否决 `DAILY_STOCK_UNITS` 常量**：1140 是**特定客流与菜单组合**下的单日需求，不是常量。
实测同一局里 easy D20 客流 78 人、D30 只有 25 人 —— 同一个 1140 在这两天分别等于
"刚好够"和"够 3 倍"，必有一边误报。而客流/菜单/客群每天都在变。
⇒ **扫参结论是分析用，不是运行时常量**（这是本轮第 5 次"把分析值当配置"的同类风险）。

替代做法（零新常量，全用现成函数）：吸底栏直接读 `trafficOf()` 与 `maxOrdersFromStock(s)`，
着色复用 `adviceOf` 已有的 `stockOrders < predicted * 0.75`（engine.js:6284）——
当前 v1.0.6 就是这么实现的（`js/ui.js:1002` 同一行 0.75），
所以不会出现"建议卡说缺料、吸底栏说够"的自相矛盾。

### 一条方法学（本轮第 4 次同类错误）

> 任何"看起来有效"的改动，要分清它是**修好了**，还是**少走了一步**。

- `storage` 第 4 级的"断崖"不是"第 4 级值钱"，而是 `420+720=1140` 刚好跨阈值（这解释了 L5 之后立刻掉到 2.88）。
- `BASE_STORAGE 600` 的"有效"不是修好了，而是让 AI 少买了一级升级。

### V22 最终顺序（不变，且更强）

```
分店改造（+300 库容/店 · 客流 +60%→+20% · DAILY_STOCK_UNITS · 三处显性化）
  → 重测（阈值一动，0%→42%→92% 的跳变会重演）
  → 最后才标定 goal
```

### 附：库容阈值换算成「人」（V22 实现时的口径）

阈值本身是"单位"，实现时要用"人"，换算链：单杯均耗 **6.0 单位**（boba 茶2+奶2+珍珠1+糖1）
× `avgCupsPerOrder` **1.55** ⇒ `可服务人数 = 库容 ÷ 6 ÷ 1.55`。

| 库容 | 可卖杯 | 折合人数 | 实测过关 |
|---|---|---|---|
| 420（现行 BASE） | 70 | **45 人** | 0% |
| 780 | 130 | 84 人 | 0% |
| 960 | 160 | 103 人 | 42% |
| **1140（阈值）** | 190 | **123 人** | **92%** |
| 1420（BASE + 2 店 × 500） | 237 | 153 人 | 92% |

对照 normal 日均客流 64~70 人：**420 ≈ 0.7 天库存，1140 ≈ 1.5~1.9 天**。

⚠️ 三个必须随身带的限定：单杯用量随菜单 5~7（±20%）、`avgCupsPerOrder` 随客群 1.0~2.0、
客流随天 40~90。**所以实现口径写成「库容 ≥ 1.5 天客流用量」，运行时判
`maxOrdersFromStock(s) / trafficOf(s) >= 1.5`，不要把 1140 写成常量**
——这与本节"否决 DAILY_STOCK_UNITS"是同一条纪律：**扫参结论进文档，不进运行时**。

### 本轮三条被实测撤回的建议（记录，防止下一轮重提）

| 建议 | 撤回原因 |
|---|---|
| AI 产能判据 `lost` → `waitLost` | A/B 掉两成（easy 100%→33%），且 `waitLost` 实测 0.0% |
| `storage.max` 6 → 10 | 分段曲线：L7 起 0.85/¥1、L8 以上 AI 根本不买 |
| `BASE_STORAGE 600` 单独有效 | 600 仍 0% 过关；它只是让 AI 少买一级，最终落在 1140 压线 |

### 两个"内容级口径缺口"（V22 必须补，否则基准永远缺块）

| 缺口 | 规模 | 修法 |
|---|---|---|
| 托管（`setStoreAuto` 从未被调用） | 约 1500 行结算逻辑 | AI 加 1 行调用（branch ≥ 2，**不要指总店**） |
| 随机事件（`resolveEvent` 从未被调用） | 20+ 条、含 ¥300~1200 的取舍 | AI 加 1 行（按 EV 选最优） |

这两条不补，"难度/收益"的标定就会一直少一块——本轮所有数字都是在"没托管、没事件"的世界里测的。

## 十四、V22 第一步落地：分店改造（扩张从需求端搬到供给端）

### 改了什么

| 项 | 原值 | 新值 | 原因 |
|---|---|---|---|
| `CFG.BRANCH_TRAFFIC` | 0.60 | **0.20** | 客流加成砍到两成，只保留"扩张的甜头" |
| `CFG.BRANCH_STORAGE` | — | **300/店** | 新增：每开一家分店 +300 库容（1 店 720 / 2 店 1020 / 3 店 1320） |
| `buyIng` 超容行为 | 整单拒绝 | **部分成交** | 仓库是容器，装满就是装满 |
| 三档目标 | 50000 | **55000** | 产出上移后同步 |

### 为什么 +500 → +300

A/B 给的推荐值是 +500，但那是在**强制开店**口径下测的。换成自然口径后 AI 自己会开到 2 家店，
+500 直接给到 1420（越过阈值太多）→ 一键补货口径产出从 6.2 万冲到 **7.7 万（154%）**，
而手搓口径只有 5.1 万：两个口径被拉开 25k，目标就再也定不准了。
+300 的阶梯是 720 / 1020 / 1320 —— 第一次扩张仍不够（720 < 960 阈值带）、第二次踩进去、第三次越过。
**扩张收益横跨三次决策**，不会让"会点一键补货的人"一步登天。

### 顺手修掉的机制性缺陷：超容整单拒绝

`buyIng` 原来是 `if (invUsed + qty > cap) return 失败` —— 想买 60 个、只剩 20 个位置，
结果**一粒都没买进来**，还得回去数仓位再改数字重试。

它惩罚的恰好是"手动操作"：一键补货自己按剩余仓位算，从不触发；手搓每次都撞墙。
**一个只惩罚手动操作的规则，等于在教玩家"别动脑，点按钮"。**

改成部分成交后（`capped: true` 回传，UI 提示"仓库快满：只买进 N 个"），
手搓口径明显回升：easy **25% → 47%**、normal **11% → 25%**。

### 现在的三档（cards=none · n=20/档）

| 档 | 目标 | autoFill 过关 | manual 过关 | 破产（autoFill） |
|---|---|---|---|---|
| easy | 55000 | 95% | 47% | 1/20 |
| normal | 55000 | 89% | 25% | 1/20 |
| hard | 55000 | 70% | 0% | 0/20 |

对比改造前：easy 破产 **4/20 → 1/20**（−60%），三档过关率首次形成 95/89/70 的梯度。
hard 在手动口径下仍是 0% —— 那是因为 55000 已经高于手搓均值（44.9k），**属于设计意图**，
不是缺陷；但这条要记着：如果以后想让手搓也能过 hard，得从产出端下手而不是压目标。

### 还没做（下一步候选）

1. **研发页首屏还给研发**：解锁 4 款配方即失效（D3~D4 起），是"后期没有新决策"最直接的一处。
2. **升级页按价值重排 + 训练改轴**：training 与 speed 抢同一个分母，两条并排卖且互相贬值。
3. **手动买料的数量控件**：现在只有 +1/+10/一键补货，缺"买够今天需要的量"这个档位。

## 十六、升级体系整理：让"买什么"这件事说真话

### 问题一：展示顺序和价值顺序是反的

旧顺序 `speed / decor / menu / storage / training / auto`：

| 项 | 实测 ROI | 旧排名 |
|---|---|---|
| storage 冷链仓库 | **4.84** | 第 4 |
| menu 招牌展位 | 1.51 | 第 3 |
| decor 门店装修 | 0.90 | 第 2 |
| speed 极速封口机 | **≈0** | **第 1** |
| auto 外卖接单 | −0.24 | 第 6 |

最该少买的排第一，唯一 ROI > 2 的排第四。玩家第一眼看到的就是错的那个。

**改法**：`UPGRADE_VALUE_ORDER` + `upgradesByValue()`，顺序集中一处、两端共用。
没有直接重排数组 —— 每个升级项都带着解释性注释，重排会把注释和对象拆散；
而"顺序"本身是展示决策，以后调它不该动数据。新增项忘了登记会被兜底追加到末尾。

### 问题二：training 与 speed 抢同一个分母

```
serviceRaw = BASE_SERVICE / (1 + 0.20·speed) / (1 + 0.12·training)
```

两条并排卖、互相贬值，而且**都被 `MIN_SERVICE`(0.4s) 夹死**。
实测 easy 的触底板只要 4 级 —— training 的加速完全被吃掉，
而界面上它还写着"+12% 出杯速度"。

**改法**：training 改挂「每杯成本」`−4%/级`（max 5 → −20%）。

- 落在**实测有效的轴**上（原料约占营收 25%，折合净利约 +5%）
- 与 menu 的 ROI 1.51 同量级，不至于变成必买项
- 出杯时间公式现在只有 speed 一个变量，`upgradeSaturated` 的触底判断也随之更干净

### 顺手修掉一处会显示错数字的地方

H5 有**两处**自己重算"单杯耗时"（`ui.js` 与 `main.js` 的实时刷新），
training 改轴后会显示错误的秒数。改成直接调 `serviceTimeOf(s, null)`。
> 这就是"同一公式抄两遍"的代价：改了引擎，界面悄悄说谎。

### 判据也要防误报

`diag` 新增的「研发树是否在首屏」只对竖屏生效。
横屏 844×390 的内容区只有两百多像素，任何长页面都要滚动 ——
在那里要求"树在首屏"等于要求横屏没有滚动，**是判据错了，不是布局错了**。

### 结果

| 档 | 改前过关 | 改后过关 | 均值变化 |
|---|---|---|---|
| easy | 95% | 100% | 69.1k → 74.0k |
| normal | 89% | 95% | 61.4k → 60.7k |
| hard | 70% | 70% | 57.4k → 56.8k |

变化在抽样噪声内（normal/hard ±1%），**不需要重标目标**。
easy 的 +7% 主要来自两颗破产局没跑到终点（样本噪声），不是训练改轴带来的。

## 十七、线上留存补洞：装到桌面（PWA）

### 为什么这件事排在这里

线上版是网页。玩家关掉标签页 = 卸载，下次要重新找链接。
而`装到桌面`之后：图标在桌面、能离线启动（SW 已就位）、点开就是游戏 ——
**这是网页版留存漏斗里唯一还能补上的一个大洞。**
（分享卡解决"别人怎么进来"，这一条解决"进来的人怎么留下"。）

### 三种环境必须分开处理

| 环境 | 能做什 么 | 处理 |
|---|---|---|
| Android / 桌面 Chrome | `beforeinstallprompt` 可程序化弹安装 | 拦截事件、自己保存，等玩家点了再弹 |
| iOS Safari | **不支持**程序化安装 | 给「分享 → 添加到主屏幕」图文说明 |
| App（Capacitor）/ 已装到桌面 | 本来就是装好的 | **不显示**，否则只会让人困惑 |

**关键细节**：`beforeinstallprompt` 必须 `preventDefault()` 并自己保存。
不拦的话浏览器会按自己的时机弹，而那个时机通常是"刚进页面"——
玩家还不知道游戏是什么，转化最低。

### 入口放在哪、为什么不弹窗

开始界面底部一个按钮「📲 装到桌面 · 断网也能玩」，**默认隐藏**，
只在不具备"已安装"条件时才出现。

没有做"到 Day 3 弹一次"这类主动引导 ——
小游戏的调性是不打断，而这个按钮常驻在开始界面，想装的人随时能点。

### 回归锁（check-web 35 项）

- 按钮存在 / 接管 `beforeinstallprompt` / 有 `preventDefault()`
- 已装到桌面（standalone）不提示
- App 内不提示（与 SW 注册各判一次）
- iOS 用的说明条样式存在

> 顺手删掉了一条我自己写的恒真断言（`x === false || true`）——
> 恒真的断言不会变红，只会让"35 项通过"看起来比实际更可靠。

## 十八、策略卡：从「都不选」到「拿卡 +4%~5%」

### 先逐张测，别再猜

之前只知道"整体负期望"（none > random > first），但不知道是哪张在亏。
先给 `--cards=<卡id>` 加单卡口径，再逐张对比"什么都不拿"：

**首测：12 张里 11 张负，只有 premium 正（+1.6%），合计拖累 40pp。**

### 根因：降本卡的收益是纸面的

`net = revenue − cogs − wages − rent` 只是**报表**，现金实际是
「买入时扣」+「打烊扣工资租金」—— 原料钱在买入那一刻就付过了。

于是 `cardMul('cogs')` 乘在 `sim.cogs` 上，**只让报表变好看，玩家一分钱没少花**；
而同一张卡的代价（`wage +7%` / `rent +6%`）**是真扣现金的**。

这解释了全部反常：
- kitchen（成本 −14% / 工资 +7%）→ 纯负
- bulk（成本 −15% / 租金 +6%）→ 纯负
- prefab（速度 +12% / 成本 +4%）→ 纯负

**修法**：把折扣落到 `buyIng` 的单价上（买入即便宜），`costOf` 同步乘同一个系数，
保证「菜单上的毛利」和「实际花掉的钱」是同一个数。

修完重测：**负卡 11/12 → 5/12**，kitchen +5.3%、takeout +3.9%、express +2.0% 全部转正。

> 这是本轮第 4 次同类问题：**效果挂在一个不产生后果的量上**。
> 前三次是合同读 `undefined` 字段、training 挂在被夹死的出杯时间、speed 触底后仍可购买。

### 再系统性地把代价压回可承受区间

单卡差异在 n=12~14 时已经落在噪声里（基线自己就在 ±3% 漂），
所以不继续逐卡抠，改为一次性：**收益 ×1.2、代价 ×0.7、绝对扣款 ×0.7**。

### 结果（normal，n≈20/档）

| 口径 | 均值 | 过关 |
|---|---|---|
| 不拿卡 | ¥62.6k | 79% |
| 随机拿 | ¥65.2k | 100% |
| 总拿第一张 | ¥65.9k | 95% |

**拿卡终于比不拿好（+4%~5%）** —— 卡池从一个"负期望门面"变成了真实的正向决策。

### 顺手把文案交给数据生成

批量调参后，12 张卡的 `cost` 文案全部过期（写着"每杯 −¥0.5"，实际 0.35）。
这已经是本轮第二次「界面说谎」，所以不再手写：

- `gain` / `cost` 由 `fx` 生成（`boost` 里的键 = 收益，其余 = 代价）
- `check-balance` 加一条断言：每张卡的收益文案必须与其 `boost` 键的百分比一致

同时 `probe` 的共鸣断言（I5a~I5c）原来写死了 `1.25×1.10×0.93`，
一改卡就红 —— 改成从卡表推导，只把共鸣倍率（1.10/1.25）当规则保留。
