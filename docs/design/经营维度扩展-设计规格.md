## 一、数据表结构变更

### 1.1 设计原则

| 原则 | 说明 |
| --- | --- |
| **字典与业务分离** | 场地类型、行政区划放**字典表**，不放业务表的 ENUM。ENUM 改值要 DDL，字典表只要 INSERT |
| **全部可空 + 应用层兜底** | 新增列一律 `NULL` 允许，存量行不回填，由应用层读到 NULL 时给默认值。避免上线即锁表 |
| **不留冗余快照** | 场地类型存 id 不存 name；展示时 JOIN 字典。字典改名不影响历史数据 |
| **坐标系显式冗余** | 坐标单独存 `coord_sys` 列。GCJ-02 / BD-09 / WGS-84 混用会差 300~600 米，靠约定迟早出事，写进数据 |
| **不建外键，用应用层保证** | 字典表会被运营增删，外键会让"下线一个类型"变成批量删门店。参考本项目既有做法（同理） |

### 1.3 字典表：行政区划

```sql
-- 省级行政区（GB/T 2260，代码 2 位）
CREATE TABLE `dict_region_province` (
  `code`       CHAR(2)      NOT NULL COMMENT 'GB/T 2260 省级代码，如 44',
  `name`       VARCHAR(32)  NOT NULL,
  `sort_no`    INT          NOT NULL DEFAULT 0,
  `status`     TINYINT      NOT NULL DEFAULT 1,
  `updated_at` DATETIME     NOT NULL DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP,
  PRIMARY KEY (`code`)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COMMENT='省级行政区';

-- 地级市（代码 6 位 = 省 2 位 + 市 2 位 + 顺序码 2 位）
CREATE TABLE `dict_region_city` (
  `code`       CHAR(6)      NOT NULL COMMENT 'GB/T 2260 地级市代码，如 440300=深圳市',
  `name`       VARCHAR(32)  NOT NULL,
  `province_code` CHAR(2)   NOT NULL,
  `sort_no`    INT          NOT NULL DEFAULT 0,
  `status`     TINYINT      NOT NULL DEFAULT 1,
  `updated_at` DATETIME     NOT NULL DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP,
  PRIMARY KEY (`code`),
  KEY `idx_province` (`province_code`, `status`, `sort_no`)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COMMENT='地级市';

-- 区县（代码 6 位，**前 4 位 = 所属地级市的前 4 位**）
CREATE TABLE `dict_region_district` (
  `code`       CHAR(6)      NOT NULL COMMENT '如 440305=深圳市南山区；前4位与 city.code 前4位一致',
  `name`       VARCHAR(32)  NOT NULL,
  `city_code`  CHAR(6)      NOT NULL COMMENT '所属地级市代码',
  `sort_no`    INT          NOT NULL DEFAULT 0,
  `status`     TINYINT      NOT NULL DEFAULT 1,
  `updated_at` DATETIME     NOT NULL DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP,
  PRIMARY KEY (`code`),
  KEY `idx_city` (`city_code`, `status`, `sort_no`)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COMMENT='区县（可选粒度）';
```

**关于区县表的一个坑**：地级市代码是 **6 位**，区代码也是 6 位，两者**前 4 位相同**（`440300` / `440305`）。
所以"区是否属于某市"的判定必须比对 `LEFT(city_code,4) = LEFT(district.code,4)`，
写成整等比较会永远不匹配 —— 区级会被静默丢弃。本项目的 K2b/K4i 就是锁这个的。

**关于数据来源**：区县全国 2900+ 条且**每年调整**（新设、撤并、改名）。
不建议手工维护，建议：
- 初始化时导入民政部《行政区划代码》库（GB/T 2260）的当期快照；
- 建一个**按年核对**的离线任务，差异输出到运营后台；
- 区县是**可选粒度**：某城市没有区县行时，门店只存到市级，**不算错误**。

## 二、字段校验规则

全部在**服务端**执行（前端校验只为体验，不能只信前端）。分三层：

### 2.1 场地类型

| 规则 | 实现 |
| --- | --- |
| 非空 | 经营中的门店必填；草稿态可空 |
| 必须是 `dict_venue_type` 中存在且 `status=1` 的 id | 查字典表 |
| 长度 ≤ 32 | Bean Validation `@Size(max=32)` |

```java
@NotBlank(message = "经营场地类型不能为空")
@Size(max = 32, message = "场地类型标识超长")
private String venueType;
```

服务端逻辑：

```java
if (!venueTypeRepo.existsEnabled(shop.getVenueType())) {
    throw new BizException("未知的经营场地类型：" + shop.getVenueType());
}
```

> **不静默回退**：非法 id 直接报错，不替换成默认值。
> 否则运营传错了 id 也不知道，数据里悄悄变成"社区"，问题会被埋很久。
> （**历史数据**的兜底在读取侧做，见第四节，那是另一回事。）

### 2.2 城市三级

| 规则 | 实现 |
| --- | --- |
| 城市必填，且必须存在于 `dict_region_city` | 查字典表 |
| `provinceCode` 必须等于 `city_code` 的前 2 位 | 以**城市为准**反查省 |
| 区级可选；有值时必须是 6 位数字 | 正则 `^\d{6}$` |
| 有区级时 `LEFT(district_code,4)` 必须等于 `LEFT(city_code,4)` | 防「市=北京 区=深圳区」 |
| 限定中国大陆 | 字典表本身只有大陆 + 台港澳，无境外 |

```java
@NotBlank(message = "经营城市不能为空")
@Pattern(regexp = "^\\d{6}$", message = "城市代码格式不正确")
private String cityCode;

@Pattern(regexp = "^\\d{6}$", message = "区级代码格式不正确")
private String districtCode;   // 可空
```

```java
// 以城市为准反查省；区级前缀必须匹配城市
String cityCode = shop.getCityCode();
RegionCity city = cityRepo.findByCode(cityCode)
        .orElseThrow(() -> new BizException("经营城市无效：" + cityCode));
shop.setProvinceCode(city.getProvinceCode());

if (StringUtils.hasText(shop.getDistrictCode())) {
    if (!StringUtils.startsWith(cityCode, shop.getDistrictCode().substring(0, 4))) {
        throw new BizException("区级与所选城市不匹配");
    }
}
```

> **为什么省要反查而不是直接存用户的值**：省是冗余字段（一个城市只属于一个省）。
> 让它永远由城市推导，就不会出现「省=北京 市=深圳」这种自相矛盾的组合。

### 2.3 地图坐标

| 规则 | 实现 |
| --- | --- |
| 经纬度**必须同时有值或同时无值** | 半个坐标没有意义 |
| 经度 ∈ [73.5, 135.1]，纬度 ∈ [3.2, 53.6] | 中国境内包围盒 |
| 必须是有限数（挡 NaN / Infinity） | `Double.isFinite` |
| 精度截断到 6 位小数 | 超出部分是 GPS 芯片噪声，不是精度 |
| `coordSys` 固定 `GCJ02` | 写库前强制 |

```java
public static Optional<GeoPoint> normalize(Double lng, Double lat) {
    // ① 先挡非有限数：NaN 与任何值比较都是 false，
    //    范围比较这一关根本拦不住它，必须单独判。
    if (lng == null || lat == null) return Optional.empty();
    if (!Double.isFinite(lng) || !Double.isFinite(lat)) return Optional.empty();
    // ② 境内包围盒（粗校验，只挡离谱错值）
    if (lng < 73.5 || lng > 135.1) return Optional.empty();
    if (lat < 3.2  || lat > 53.6)  return Optional.empty();
    // ③ 精度：6 位小数 ≈ 0.11 米，再多是噪声
    return Optional.of(new GeoPoint(
        BigDecimal.valueOf(lng).setScale(6, RoundingMode.HALF_UP).doubleValue(),
        BigDecimal.valueOf(lat).setScale(6, RoundingMode.HALF_UP).doubleValue(),
        "GCJ02"));
}
```

**关于包围盒的边界说明**：包围盒只能拦住「离谱」的错值（多输两位、误传境外坐标），
**不能**据此判断坐标是否属于某个城市 —— 城市真实边界是不规则多边形。
「门店坐标是否落在所选城市内」需要高德逆地理编码（`AMap.Geocoder` 的 `regeocode`）
拿到真实 `adcode` 后与 `city_code` 比对。本项目没有内置该校验，因为小游戏端拿不到高德 SDK。

## 三、地图选点交互逻辑

### 3.1 合规前提（必读）

国内地图服务必须使用**有测绘资质**的服务商（高德 / 百度 / 腾讯）。
本次选定**高德**，坐标口径 **GCJ-02**。

三种坐标系**不可混用**，同一地点在它们之间可差 **300~600 米**：

| 坐标系 | 来源 | 说明 |
| --- | --- | --- |
| **GCJ-02** | 高德 / 腾讯 / Google 中国区 | 本项目采用 |
| BD-09 | 百度 | 与 GCJ-02 还差一层百度自己的偏移 |
| WGS-84 | GPS 芯片原始输出 | 高德/百度显示前都要先转换 |

**因此**：`coord_sys` 必须是数据的一部分，而不是"大家都知道用高德"。

### 3.2 交互流程

```
用户点击「在地图上选点」
   ↓
前端检测 coordSys 是否为 GCJ02；不是则先转换（后端接口 /convert）
   ↓
打开高德地图（JS API Map + Marker，可拖拽）
   ↓
用户拖动 / 点击选点
   ↓
前端 reverseGeocode(lng, lat) 拿到行政区信息
   ↓
  ┌─ 反查出的 cityCode 与门店已选城市一致？ ──┐
  │                                          │
  是 → 回填坐标，标记 coordSys=GCJ02         否 → 提示「该坐标不在已选城市内，
                                                要改城市还是只更新坐标？」，
                                                用户选择后同步更新 city_code
   ↓
提交后端 → 服务端再做一次第三节的全部校验（前端校验只防手抖，不防篡改）
```

### 3.3 前端实现要点

```js
// ⚠️ 示例中的 key 必须从后端下发，不能硬编码在前端包里
const map = new AMap.Map('container', {
  center: [DEFAULT_LAT, DEFAULT_LNG], zoom: 12,
  // 关键：Map 实例不设置 mapStyle，避免加载非高德底图
});
const marker = new AMap.Marker({ position: [lat, lng], draggable: true });
map.add(marker);

marker.on('dragend', e => {
  const p = e.lnglat;                       // GCJ-02
  // 逆地理编码确认行政区，避免「在深圳的坐标 + 北京的城市」
  new AMap.Geocoder().getAddress(p, (status, result) => {
    if (status === 'complete') {
      const adcode = result.geocodes[0].adcode;  // 6 位地级市代码
      if (adcode !== form.cityCode) {
        Modal.confirm(
          `该坐标位于${result.geocodes[0].city}，与已选的${form.cityName}不一致`,
          { okText: '同时把城市改为该地', cancelText: '只改坐标' }
        );
      }
    }
  });
});
```

### 3.4 不内嵌地图 SDK 的降级方案

本项目（H5 静态托管、小游戏端无 DOM）**没有内嵌高德 SDK**，而是：

| 方案 | 说明 |
| --- | --- |
| **手输坐标** | 默认路径。两个输入框 + 「定位」按钮，校验在引擎 |
| **跳转高德查坐标** | 按钮打开高德地图网页版选点，复制坐标回填 |
| **内嵌 SDK（生产建议）** | 把上面这段替换掉输入框即可；**存储结构与校验逻辑都不用动** |

不内嵌 SDK 的理由：
1. 静态托管/离线环境拉不到瓦片，地图区会空白 —— 比没有地图更糟（用户以为坏了）
2. 内嵌 SDK 会让一个外部脚本成为页面硬依赖，还要管密钥与合规责任

## 四、对已有数据的兼容

### 4.1 兼容策略总原则

> **新增字段一律"可空 + 应用层兜底"，不升级 schema 版本、不回填存量数据、不加外键。**

原因：回填 1000 万行会给上线窗口带来压力，而这三个字段**都不影响历史业务的正确性**
（老门店的经营信息就是"未知"，而不是"错"）。

### 4.2 上线步骤

```sql
-- Step 1：建字典表并灌初始数据（不影响业务表）
-- Step 2：业务表加列，全部允许 NULL（MySQL 8.0 加列是 INSTANT DDL，不锁表不重建）
-- Step 3：发新版本。应用读到 NULL 时给默认值
-- Step 4：观察 1~2 个版本，确认没有异常后再考虑给存量行回填
```

### 4.3 存量行读出时的兜底

```java
/** 存量行（三个字段都是 NULL）的兜底。
 *  注意：这是**读取侧**兜底，与写入侧的"非法即报错"是两件事 ——
 *  历史数据不能因为不合法就让门店打不开。 */
public VenueInfo resolveVenue(Shop shop) {
    String type = Optional.ofNullable(shop.getVenueType())
            .filter(venueTypeRepo::existsEnabled)
            .orElse(DEFAULT_VENUE_TYPE);          // "community"
    String city = Optional.ofNullable(shop.getCityCode())
            .filter(cityRepo::exists)
            .orElse(DEFAULT_CITY_CODE);          // "110100" 北京市
    // 坐标：非法就当"未选点"（null），不要兜一个默认坐标 ——
    // 兜底坐标会让门店看起来"已经定位在北京天安门"，是**编造数据**。
    GeoPoint geo = normalize(shop.getLongitude(), shop.getLatitude()).orElse(null);
    return new VenueInfo(type, city, geo);
}
```

### 4.4 三类脏数据的处理

| 场景 | 处理 |
| --- | --- |
| 三列全 NULL（存量行） | 场地→社区，城市→北京，坐标→未选点 |
| id 不在字典里（脏数据/字典下线） | 读取时退默认，**不改库**；运营后台提供"一键修复" |
| 越界/NaN 坐标 | 视为未选点；告警日志打出来 |

### 4.5 与本项目既有做法的一致性

bubble-tycoon 的存档兼容完全靠 `sanitizeState`（清洗器）：`importSave` 只认 `s.v === 2`，
**新增字段不升版本号**，而是让清洗器补默认值。

```js
s.venue = sanitizeVenue(s.venue);
```

`importSave` 里有 `raw.v !== 2` 就直接拒绝 —— 如果为新特性升版本，
**所有存量存档会立刻打不开**。这正是要避免的，所以版本号保持不变。

> 迁移到 Java 后端时同理：不要因为加了字段就改接口的 `schemaVersion`，
> 否则老客户端会全部拿不到数据。

### 5.1 查询字典：场地类型

### 5.5 坐标系转换（对外提供 WGS-84 时）

```

```

## 六、Java 侧字段定义

```java
public class ShopVenueDTO {
    @NotBlank @Size(max = 32) private String venueType;
    @NotBlank @Pattern(regexp = "^\\d{6}$", message = "城市代码格式不正确") private String cityCode;
    @Pattern(regexp = "^\\d{6}$", message = "区级代码格式不正确") private String districtCode;
    /** 经度 GCJ-02；DECIMAL(10,7) → BigDecimal 更稳 */
    private BigDecimal longitude;
    private BigDecimal latitude;
    @Pattern(regexp = "^(GCJ02|BD09|WGS84)$", message = "坐标系不支持")
    private String coordSys;
    private LocationSource locationSource;
    private LocalDateTime locationTime;

    public enum LocationSource { MAP_PICK, MANUAL, LEGACY }
}
```

> `coordSys` 用**枚举而不是字符串**：`BD09` 和 `GCJ02` 拼错一个字母，
> 在字符串场景里完全不会报错，坐标直接偏 500 米。

## 九、遗留与建议

| 项 | 说明 |
| --- | --- |
| 区县数据同步 | 全国 2900+ 且逐年调整，建议接行政区划库按年核对，不手工维护 |

| 多门店 | 本设计是单门店维度；连锁场景建议 `shop_id` 与门店表一对多，坐标落在门店而非商家 |
