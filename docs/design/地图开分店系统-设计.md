# 「地图开分店」系统 · 数据结构与关键逻辑设计

> 先定数据结构与逻辑，再改代码。理由：这次是**数据模型重构**，
> 动之前必须先想清楚"哪些字段是权威、哪些是派生"——
> 否则会出现"两处都存店数，改一处忘另一处"的经典 bug。

---

## 一、核心决策：`s.stores[]` 权威，`s.shops` 降级为派生值

### 问题

现有 `s.shops` 是一个**数字**（1 = 只有总店，2~4 = 有分店）。
它同时表达了三件事：

1. 有几家店
2. 店号范围（`1..s.shops`）
3. 店的位置（隐含按顺序排列，第 i 家就是 branch i）

新需求要"任意位置开设分店"、每店有独立名称/坐标/等级/账本，
数字**表达不了**这些 —— 必须变成对象数组。

### 风险

`s.shops` 在 engine.js 里有 **19 处**使用点。如果直接把它改成数组，
所有 `s.shops++`、`pos(s.shops, 1)`、`s.shops - 1` 都要改，
且**极容易漏**（漏一处就是"开了店但店号算错"这类静默 bug）。

### 解法

```js
s.stores = [ {...}, {...} ]   /* 权威：店数、店号、位置、账本 */
s.shops  = s.stores.length   /* 派生：保留给既有 19 处代码用 */
```

**关键**：`s.shops` 仍然存在、仍然含义不变（总店数），
既有代码一行都不用改。改动只发生在：
- 读 `s.shops` 的地方**不用动**
- 写 `s.shops` 的地方（目前只有 `openShopBranch` 里的 `s.shops++`）
  改成"push 一个 store + 同步 `s.shops`"

**同步点必须收口到一个函数** `syncShopCount(s)`：
任何增删店的地方都调它。散落着 `s.shops = X` 就会漂。

## 二、`s.stores[]` 字段设计

```js
{
  id: 1,                    /* 稳定 id（不随顺序变化） */
  branch: 1,                /* 店号：1 = 总店，2+ = 分店。
                               与 staff.branch / manager.branch 对齐，
                               既有代码的 staffOfBranch(s, b) 不用改 */
  name: '总店',              /* 玩家可改 */
  emoji: '🏠',
  cityId: '110100',         /* 所在城市（决定可用菜系） */
  venueType: 'community',   /* 场地类型（决定客流特征） */
  lng: 116.407,             /* 地图坐标（GCJ-02） */
  lat: 39.909,
  coordSys: 'GCJ-02',
  isMain: true,             /* 主店标记，全表唯一 */
  level: 1,                 /* 店铺等级（1~10） */
  exp: 0,                   /* 升级经验 */
  auto: false,              /* ★ 托管标记：true = 交给店长自动经营 */
  managerId: null,          /* 该店店长（null = 玩家亲自经营） */
  cash: 0,                  /* 该店自有资金 */
  inv: {},                  /* 该店独立库存 */
  income: 0,                /* 累计营收 */
  expense: 0,               /* 累计支出 */
  cups: 0,                  /* 累计出杯 */
  days: 0,                  /* 营业天数 */
  lastReport: null,         /* 最近一份经营报表 */
  history: [],              /* 近 7 天报表摘要 */
  upgrades: {},             /* 该店专属升级（预留） */
}
```

### 为什么 `branch` 与 `id` 并存

- `id` 稳定不变（存档、引用用）
- `branch` 是"显示序号"（第几家店），与既有 `staff.branch` 语义一致

两者分开后，将来"关店"导致序号重排时，存档里的引用不会错乱。
本轮不实现关店，但字段先留对 —— **数据结构改一次很贵，先改对**。

### 主店唯一

`isMain` 全表最多一个。第一家店（branch 1）默认是主店。
玩家可以把任一店设为主店 —— 设 A 为主店时，A 自动成为主店、
原主店自动取消（**原子操作**，不能出现"两家主店"或"没有主店"）。

主店有**唯一店长** —— 与分店同样的规则：每店最多 1 名店长。

## 三、店长名额规则的变化

### 现状（V11）

```
名额 = s.shops - 1 - 已招店长数
```

总店不设店长（玩家自己经营总店）。

### 新需求

> 每家分店最多任命 1 名店长（**含主店**）。

### 新规则

```
名额 = s.shops - 已招店长数
```

**总店也可以有店长了**。这是需求明确要求的。

⚠️ 连带影响：V11 的 `managerSlotsLeft` 语义变了，
而 probe 的 N1 组断言的是旧语义 —— 必须同步更新断言，
否则会出现"测试全绿但规则已错"的假象。

### 店长的归属

V11 里 `manager.branch` 表示"他管第几家店"。
新模型里店长是**挂在店上的**（`store.managerId`），
但 `manager.branch` 字段保留（作为冗余的"当前所在店"），
两者由 `syncStoreManagers(s)` 保持一致。

保留冗余的理由：既有 15 处 `managerOfBranch` 调用不用改。
**冗余字段必须有单一同步点**，否则就是 bug 温床。

## 四、玩家接管 / 托管

### 状态

```js
store.auto = false   /* 玩家亲自经营 */
store.auto = true    /* 店长自动经营 */
```

### 规则

| 情况 | 效果 |
|---|---|
| 未指派店长 | 只能玩家经营（`auto` 恒为 false） |
| 已指派店长 | 可在「玩家接管」与「交给店长」间切换 |
| 玩家接管 | 该店的员工回到玩家直接指挥（进工位） |
| 交给店长 | 该店由店长 AI 经营（不进实时营业模拟） |

### 关键：托管的店还参与实时营业吗？

**不参与。** 托管的店由店长 AI 在每日结算时独立结算，
不进入 `openShop` 的实时模拟（那会需要玩家逐个点击出杯位）。

这带来一个必须处理的问题：**实时模拟的客流怎么算？**

现状：`trafficOf` 用 `1 + 0.6 × (在营店数 − 1)`。
托管的店不产出会导致客流虚高。

**解法**：`activeBranchCount` 只数「玩家在营」的店
（`!store.auto` 且有员工），托管店不计入。

## 五、店长 AI 每日经营

### 触发时机

`nextDay` 里，与 `managerDaily`（补员）相邻但独立。

```
nextDay:
  ...
  dailyManagerRefresh(s)     /* 候选刷新 */
  managerDaily(s)            /* 店长补员 */
  managedStoresDaily(s)      /* ★ 托管店结算 */
```

### 单店结算流程

```
1. 校验：store.auto && store.managerId 有效
2. 该店有无员工？无 → 跳过（空店不产出，记「空转」）
3. 计算客流（按该店城市 / 场地 / 等级）
4. 计算营收 = 客流 × 客单价 × 店长加成
5. 扣成本：
     原料成本（店长自己采购 → 从该店 cash 扣）
     员工工资（该店员工工资）
     店铺租金（按等级与场地类型）
6. 结算 net，加进该店 income/expense/cash
7. 店铺升级：累计营收达阈值 → level+1
8. 生成报表 → store.lastReport + store.history
```

### 店长采购规则

店长自己买原料，但**只能买该店城市能买到的**（与玩家同一约束）：

```
采购量 = min(缺货量, 该店 cash 能负担的量, 库存上限)
```

★ 店长采购**不与玩家抢库存** —— 玩家的 `s.inv` 与店长的 `store.inv` 是两套。
但店长的钱来自 `store.cash`，而 `store.cash` 初始为 0 →
**店长没钱就什么都做不了**。

### 资金来源

新开店时 `store.cash` 需要一笔启动资金。设计：

- 开店时从玩家 `s.cash` 划拨一笔**启动金**（如 ¥2000）
- 之后店长自给自足，盈利留在店里
- 玩家可以随时往店里**注资**，或从店里**提现**

这样"独立资金"才有意义，且玩家有干预手段（不能眼睁睁看店饿死）。

## 六、地图开店流程

### 为什么不内嵌地图 SDK

沿用现有「经营信息」面板的既定论证（js/ui.js 里写得很清楚）：
静态托管的离线包拉不到高德瓦片 → 地图区空白 → 反而像坏了。

### 实际交互

```
「🏙️ 店铺地图」面板
  ├─ 已有店铺列表（emoji + 名称 + 城市 + 等级 + 店长 + 今日收益）
  │    点击 → 切换控制权（接管 / 托管）
  ├─ 「＋ 开新店」按钮
  │    → 选城市（从 340+ 城市里选，与现有 city 下拉同源）
  │    → 选场地类型（10 种，已有 VENUE_TYPES）
  │    → 取该城市经纬度（CITIES 表自带 lng/lat）
  │    → 店名（默认「XX店」，可改）
  │    → 确认 → 扣 SHOP_COSTS 费用 → 建店 + 划启动金
  └─ 每店可「设为主店」「改名」「注资/提现」「任命店长」
```

**位置从哪来**：城市表自带 GCJ-02 经纬度（`CITY_GEO`），
选城市即自动定位 —— 不让玩家手输坐标（那是给"经营信息"用的专家功能）。
"任意位置"通过「选任意城市」实现，覆盖 340+ 城市。

## 七、关键不变式（要写成断言）

| # | 不变式 |
|---|---|
| 1 | `s.shops === s.stores.length`（永远同步） |
| 2 | `s.stores[0].branch === 1` 且 `isMain` 为真（总店恒存在） |
| 3 | 全表 `isMain` 最多一个 |
| 4 | 每店 `managerId` 最多一个店长（一个店长只管一家店） |
| 5 | 店长数 ≤ 店数 |
| 6 | `store.managerId` 指向的店长，其 `manager.branch` === `store.branch` |
| 7 | 托管店（`auto=true`）必有店长 |
| 8 | 玩家在营店数 ≤ 总店数 |
| 9 | 店铺坐标在境内范围且 coordSys 一致 |

### 兼容

- 员工/店长的 `branch` 引用保持有效
